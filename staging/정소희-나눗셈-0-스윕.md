## 확인한 사실
- **[src-query §3] WIDTH_BUCKET 의 NUMERIC 범위가 아주 작으면 서버 SIGFPE** (.51, e30370dc0, 2026-11-10): `db_width_bucket_calculate_numeric ()`(arithmetic.c:4533)의 가운데 몫 `(v3 - v2) / v4` 가 scale 252 아래면 `float_numeric_db_value_div ()` 가 오류 없이 0 으로 반올림하고, 두 번째 나눗셈(오름차순 :4600, 내림차순 :4666)이 `float_numeric_div_fast ()`(numeric_opfunc.c:2037)의 128비트 나눗셈에서 트랩한다. 재현 `SELECT WIDTH_BUCKET (CAST (0 AS BIGINT), CAST (-1e-252 AS NUMERIC), CAST (1e-252 AS NUMERIC), 5);` — CS 서버 core, SA 멈춤(release·debug). CBRD-26006(de7bc5ec2)부터. **수정 PR#8478(CBRD-28024, 미머지, 2026-11-11) — 범위 안 비율을 먼저 `floor ((v1-v2)/(v3-v2)*v4) + 1`, 나눌 수가 범위 폭(갈래 조건상 0 아님).**
- **[src-query §2] `float_numeric_db_value_div ()` 는 나눌 수 0 을 검사하지 않는다** (.51, e30370dc0): 피제수 0 만 본다(numeric_opfunc.c:3940 대, 주석 "already handled in parsing"). 호출자 6곳 중 파서 상수 접기·`qdata_number_numeric` 2곳·expr_compile NUMERIC 나눗셈 커널·WIDTH_BUCKET 첫 나눗셈(버킷 수 ≥ 1)이 막고, WIDTH_BUCKET 두 번째 나눗셈만 막지 않는다. 새 호출자는 0 을 먼저 막아야 한다.
- **[src-query §2] WIDTH_BUCKET 은 인자가 모두 상수여도 서버가 계산한다** (.51, fc05df9ff, CS core 로 확인): 위 재현(표 없음)의 core 스택이 `fetch_op_width_bucket ()` ← `expr_k_generic ()` — 파서 상수 접기로 클라이언트에서 끝나지 않는다.
- **[src-query §3] MD5·SHA2 가 문자 수만큼의 바이트만 해시한다** (.51, e30370dc0, en_US.utf8 SA): `db_string_md5 ()`(string_opfunc.c:3130)·`db_string_sha_two ()`(:2912)가 길이로 `db_get_string_length ()`(문자 수)를 넘긴다. `MD5 ('한글abc')` = 앞 5바이트의 MD5. SHA1(`db_string_sha_one ()`)은 바이트 수라 맞다. release/11.4 도 같다. **미수정, 발번하지 않음**(경미, 2026-11-10) — 재현 SQL claude-workspace `projects/CBRD-28024/스윕/미발번/md5_sha2_multibyte.sql`.
- **[src-query §3] MONETARY 를 음수로 나누면 "Attempt to divide by zero"** (.51, e30370dc0, SA): `qdata_is_divided_zero ()`(query_opfunc.c:4313)의 MONETARY 갈래가 `amount <= DBL_EPSILON` 이라 `fabs` 가 없다(FLOAT·DOUBLE 갈래와 파서 상수 접기는 `fabs`). `x / -2`·`10 / CAST (-2 AS MONETARY)` 도 오류. 2018 (192e75397)부터, 11.4 도 같다. **미수정, 발번하지 않음**(경미, 2026-11-10) — 재현 SQL `…/스윕/미발번/monetary_negative_divisor.sql`.
- **[src-query §2] 정수 나눗셈의 0·MIN/−1 은 위 말고는 막혀 있다** (.51, e30370dc0, 스윕): src/query·base·parser·optimizer·storage·transaction 의 정수 나눗셈·나머지 약 1,400 토큰 중 나눌 수가 변수인 약 230곳을 읽었다 — 0 검사·상수·구조상 0 불가. MIN/−1 은 MOD·`/`·DIV·컴파일된 식·집계식 융합·파서 상수 접기 모두 검사(CBRD-27229·27255). 시리얼 증분 0 은 카탈로그가 갱신 불가라 닿지 않는다(`db_serial` 은 갱신 불가 뷰, `_db_serial` 은 DBA 도 UPDATE 권한 없음). FP 예외를 켜는 코드가 없어 실수 0 나눗셈은 트랩이 아니다.
- **[src-query §3] WIDTH_BUCKET 내림차순의 범위 끝 판정이 두 경계끼리 비교한다** (.51, e30370dc0, 2026-11-11, SA·단위): `db_width_bucket_calculate_numeric ()` 내림차순 갈래가 v1 <= v3 를 볼 자리에서 `numeric_db_value_compare (value2, value3)`(arithmetic.c:4634, 이 갈래에선 늘 1)라, BIGINT·NUMERIC 피연산자가 범위 아래면 공식으로 간다 — `WIDTH_BUCKET (CAST (-3 AS BIGINT), 6, 0, 9)` = 14(정답·DOUBLE 10), 아주 먼 `(CAST (-1e20 AS NUMERIC), 5, 0, 10)` 은 `ER_QPROC_OVERFLOW_ADDITION`. 2014(6522201da)부터, release/11.4 도 같다(:4555). **수정 PR#8478 둘째 커밋(미머지).**
- **[src-query §3] `numeric_coerce_num_to_double ()` 는 높은 scale 의 정수를 1 ulp 어긋나게 낸다** (.51, b01cc2876·fc05df9ff, 2026-11-11, SA): 계수를 double 로 바꾼 뒤 `numeric_Pow_of_10_dbl[scale]` 로 나눠 두 번 반올림한다(numeric_opfunc.c:5612). `CAST (CAST (5012 AS NUMERIC (38, 34)) AS DOUBLE)` = 5.012000000000001e+03(`= 5012` 거짓). WIDTH_BUCKET 은 그 값에 floor 를 걸어 정확한 경계 값이 개수가 크면 한 칸 낮다 — `(CAST (0.50 AS NUMERIC (5, 2)), 0, 1, 2000)` = 1000(정답·DOUBLE 1001). CBRD-27178(7749f4ff8, 2026-09) 전의 `atof (계수) / pow (10, scale)` 도 같은 두 번 반올림. **미수정, 발번하지 않음**(사용자 결정 2026-11-11 "PR 밖, 기록만") — 재현 SQL claude-workspace `projects/CBRD-28024/스윕/미발번/width_bucket_boundary_floor.sql`.
