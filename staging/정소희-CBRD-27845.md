# 정소희-CBRD-27845 — 외래 키 검사가 키마다 잡은 클래스 표현·가지치기 문맥을 마지막 것만 놓는다 (src/transaction, src/storage, src/base)

기준: (.51, develop `226352283` · PR#8394 헤드 `1cc4cb1a7`, 2026-11-03). 줄 번호는 develop 기준. 대상 모듈 노트: `modules/src-transaction.md` §2·§3, `modules/src-storage.md` §2(클래스 표현 캐시), `modules/src-base.md` §2(자원 추적기).

## 확인한 사실 (develop 226352283)
- `locator_check_foreign_key ()`(locator_sr.c:4035, SERVER·SA)는 비-NULL 외래 키마다 참조 클래스 표현을 `heap_classrepr_get ()`(:4116)으로 고정하고 분할 부모면 `partition_load_pruning_context ()`(:4127)로 가지치기 문맥을 읽지만, 놓는 곳은 함수 끝 error 레이블(:4189·4195) 하나다 — 행마다 키 수 - 1 개의 고정이 남고, 분할 부모면 `partition_attrinfo_get_key ()` 가 시작한 루트 attr_info 고정과 술어 언팩까지 덮여 2개씩 남는다. INSERT(호출처 locator_sr.c:5176, `locator_insert_force ()` 안)와 UPDATE(호출처 locator_sr.c:5993, `locator_update_force ()` 안) 둘 다 — UPDATE 는 `qexec_execute_update` 가 `not_check_fk=false` 를 넘겨 바뀐 열과 상관없이 매 행 검사한다. 실측(debug, `csql -S` + gdb, 10행, get/free): FK 2개 INSERT 52/42, 같은 표의 비-FK 열 UPDATE 57/47, 분할 부모 2개 INSERT 132/112, FK 1개 42/42.
- 클래스 표현 캐시(heap_file.c): 항목 1024개 고정(`HEAP_CLASSREPR_MAXCACHE` :106)이고 늘지 않는다 — `heap_classrepr_entry_alloc ()` 의 expand_list 는 "not supported"(NULL), 그러면 `heap_classrepr_get ()` 은 캐시 밖 디스크 표현을 돌려준다. LRU 재사용은 fcnt == 0 만 고른다(:1916). 무효화 `heap_classrepr_decache_guessed_last ()`(:1449 — 루트 클래스 힙의 레코드 갱신 `HEAP_MAYNEED_DECACHE_GUESSED_LASTREPRS` :410, 트랜잭션 끝·롤백 `decache_heap_repr`)는 fcnt > 0 이면 해시·LRU 에서 떼고 force_decache 만 세운다 → 고정이 샌 항목은 서버 수명 동안 한 칸을 잃는다.
- debug(SERVER_MODE, `!NDEBUG` — CI 의 optdebug 포함) 서버는 요청마다 `db_private_alloc` 을 추적하고, 요청 끝 `net_server_request ()` → `pop_resource_tracks ()`(thread_entry.cpp:443)가 남은 할당을 서버 에러 로그에 덤프(`tracked res_ptr=… first_caller=<파일:줄>`)한 뒤 `restrack_assert (false)`(resource_tracker.hpp:426·455)로 abort 한다. 억제는 기본 꺼짐. release 는 그 뒤 `db_clear_private_heap ()`(network_sr.c:949)이 요청의 private heap 을 비우므로 요청 안의 누수가 요청을 넘지 않는다. abort 스택은 서버 `abort_handler` 가 `$CUBRID/log/coredump/cub_server_<시각>.coredump` 에 남긴다. 실측: 분할 부모 2개 표 INSERT 1행 → 덤프 `xasl_stream.cpp:85·244·254`·`heap_file.c:10611`(파티션 캐시 미적중이면 `heap_get_class_partitions` 쪽 할당까지 15건).
- 서버가 abort 하면 cub_master 가 다시 띄운다(`auto_restart_server`, 기본 yes, system_parameter.c:2242) — 크래시 직후 다른 PID 가 볼륨을 잡아 재현 스크립트의 `deletedb` 가 "in use" 로 실패했다. 정리 단계는 `server stop` 을 재시도해야 한다.
- `heap_attrvalue_get_key ()`(heap_file.c:14682)는 다중 열 인덱스 키의 midxkey 버퍼 크기를 **행 레코드 전체 길이**(`recdes->length`, :14744 — 함수 인덱스 결과를 더함)에서 잡고 `DBVAL_BUFSIZE`(4096, btree.h:531)를 넘으면 `db_private_alloc` 한다(:14756) — 키가 아니라 행이 길면(저장 길이, 즉 문자열 압축 뒤) 다중 열 키는 할당 버퍼를 갖는다. `locator_check_foreign_key ()` 는 반복문 안의 출구에서만 그 값을 비우고 error 레이블(:4188)은 비우지 않아, 오류 출구에서 남는다(**미수정 — PR#8394 두 번째 커밋**). debug 서버는 요청 끝 `restrack_assert`, 덤프 `first_caller=heap_file.c:14756`. 결정론 재현: 부모 분할 식 `100 div a` 에 a = 0 인 키 → FK 가지치기(`partition_attrinfo_get_key ()` 의 분할 식 평가)가 -539 로 끝남 + 압축되지 않는 6,144자 행(SHA-512 16진 48개). `repeat ('x', 5000)` 은 압축돼 레코드가 짧아 재현이 안 된다(실측 recdes 길이 수십~수백 바이트).
- FK 탐색(`xbtree_find_unique (…, S_SELECT_WITH_LOCK, …)`)이 기다리는 상대는 부모 **키를 넣거나 지운 트랜잭션의 MVCCID** 다(`btree_key_wait_out_conflicting_writer ()`(btree_lock.cpp:56) → `btree_key_wait_for_tran_end ()`(btree_lock.cpp:100) → `logtb_wait_for_tran_end ()` → `lock_transaction_mvccid ()`). 부모 행의 키가 아닌 열을 커밋하지 않고 UPDATE 해 둔 행 X 락은 FK 검사를 막지 않는다(실측: 6초 쥐고 있어도 자식 INSERT 즉시 성공). 락 타임아웃 재현은 부모 키를 커밋하지 않고 INSERT 해 둔 세션 + `set transaction lock timeout 1`.
- 같은 로직의 키 1개 판 `btree_check_foreign_key ()`(btree.c:26704 — 외래 키를 더할 때 기존 행을 검사하는 `xlocator_check_fk_validity ()` locator_sr.c:11919 가 부른다)는 두 출구에서 다 놓아 해당 없다.
