# 정소희 — CBRD-27143 (bind LIKE 패턴 지문) 환류 대기

작성: 정소희 (.52) · 기준 리비전 upstream/develop `c0e06bef9`~`9ee8bac8b` (수정 PR#8006) · 2026-09-22

- **[src-optimizer §2] host variable 패턴 `col LIKE ?` 도 컴파일 시 generic 파생 range 를 얻는다 — `qo_rewrite_like_terms()` 가 `pt_is_pseudo_const(pattern)` 분기에서 `qo_rewrite_like_for_index_scan()` 을 불러 `col RANGE (like_match_lower_bound(?) ge_lt like_match_upper_bound(?))` 를 붙이고 `PT_EXPR_INFO_LIKE_DERIVED_RANGE` 를 세운다** (.52, c0e06bef9, 2026-09-22): PREPARE 플랜 덤프 `term[0]: s range (like_match_lower_bound(?:0) ge_lt like_match_upper_bound(?:0)) (sel 0.1)` 로 확인. 경계가 식이라 그 항의 선택도는 기본 0.1 에 머물고(`histogram_split_hv_range()` 도 직접 PT_HOST_VAR 경계만 봄) 희귀 접두어의 인덱스 스캔 비용이 비관적. **미수정**(후속 후보). JIRA CBRD-27143 의 "리라이트 비대칭 → bounded scan 불가" 전제는 이로써 불성립.
- **[src-optimizer §2] 상수 접두어 LIKE 는 파생 경계가 접혀 자동 파라미터화되므로 같은 문장 텍스트의 모든 접두어 패턴이 XASL 캐시 엔트리 하나를 공유하고, 플랜은 첫 패턴의 값으로 고른다** (.52, c0e06bef9, 2026-09-22): `select count(pad) from t where s like 'abc%'`(sscan, sel 0.8999) 뒤 `'xyz%'` 는 플랜 덤프 없이 캐시 히트로 같은 sscan. 결과 정확, 플랜만 첫값 고정 — bind peek 의 OFF 계약과 같은 성질. 미수정(설계 사실).
- **[src-compat §2] `plan_cache_bind_sensitivity`/`BIND_SENSITIVE` 의 밴드 재플랜은 kept tree(입력 버퍼 DB_SESSION 스코프, CBRD-27231 Open) 위에서만 돌아 csql 줄 단위·CTP(JDBC 문장별)에서는 관측 불가하고, EXECUTE 들을 csql 한 줄에 이어 쓰면 관측된다** (.52, c76ac823d, 2026-09-22): LIKE 'abc%'(TABLE) → 'xyz1%' 재플랜 INDEX → 'xyz2%' 같은 밴드 무재플랜 → 'abc%' 재플랜 TABLE; `a = ?` 대조군 동일. 26959·27143 TC 가 첫 peek 만 검증하는 이유.
- **[src-compat §3] 한 줄 형태의 kept-tree 경로에서 파라미터 OFF 인데도 두 번째 EXECUTE 가 한 번 더 재플랜되고(값에 맞춰 플랜이 바뀜) 세 번째부터 유지된다 — EQ·LIKE 동일** (.52, c76ac823d, 2026-09-22): `repro/oneline_off.sql`(projects/CBRD-27143). 추정 원인: prepared 정보의 마커 XASL 이 `HV_PRED_PLAN_UNPEEKED` 를 계속 지녀 `do_get_prepared_statement_info()` 가 xasl_id 를 비우고 `do_recompile` → `do_reexecute_prepared_statement_from_kept_tree(force_replan=true)`. "OFF = 첫값 플랜 고정" 계약과 어긋남. **미수정**(CBRD-27231 과 함께 볼 것).
- **[src-compat §2] SQL PREPARE/EXECUTE 경로에서 `LIKE ?` 에 비문자열(정수)을 바인딩하면 `do_cast_host_variables_to_expected_domain()` 이 컬럼 문자열 도메인으로 캐스트해 지문·플래너가 문자열 패턴처럼 가격 매긴다(재플랜, 0행); NULL 은 `histogram_get_like_selectivity()` 타입 검사에서 success=false 라 가격 불가** (.52, c76ac823d CTP 실측, 2026-09-22).
- **[src-compat §2] `show trace` 의 `Query Plan:` 블록은 그 세션 파서가 재컴파일/재플랜해 `plan_trace` 를 남긴 실행에만 나타난다 — 첫 peek 재플랜과 한 줄 형태의 kept-tree 재플랜에서 보이고, 캐시 히트 실행에서는 없다** (.52, c76ac823d, 2026-09-22): TC 에서 "재플랜이 일어났나" 의 판정 신호로 쓸 수 있다. 한 줄 형태의 첫 `show trace` 가 `TABLE SCAN (dual)`(`trace_stats()` 자신의 플랜)을 보이는 것은 표기 잡음.
