## 확인한 사실 (develop)
- **[src-object §2] DATETIMETZ 인덱스 비교는 tz_id 를 보지 않는다** (.51, 4e389935d, 2026-11-04):
  - `mr_index_cmpdisk_datetimetz ()` 는 `mr_index_cmpdisk_datetime ()` 을 그대로 부른다(object_primitive.c:4387-4391, 주석 "tz_id is ignored"). release/11.4 도 같다(4447·4455).
  - B-tree 는 비교가 같은 키를 찾으면 새 OID 를 그 키에 덧붙인다(`btree_key_insert_new_object ()`, btree.c:32329). 그래서 같은 순간을 다른 시간대로 적은 두 값은 키 하나가 되고, 키에서 읽으면 키에 남은 한 값으로 나온다(실측에서는 먼저 넣은 `+09:00`).
  - 커버링 관문 `qo_check_type_index_covering ()`(query_graph.c:10458)·`qo_check_coll_optimization ()`(query_graph.c:10410)이 이런 타입과 대소문자 무시 콜레이션의 키를 커버링에서 빼는 이유가 이것이다.
  - 실측: PR#6466 `05b46aefe` 는 함수 결과(fi_domain)에 이 관문을 걸지 않는다. 그래서 `(i, to_datetime_tz(s))` 커버드 투영이 `+09:00` 두 번(develop `+09:00`·`+00:00`), `(n, s collate utf8_en_ci)` 류 ci 결과가 65,65(develop 65,97)다 — `repro/G1-01`.
- **[src-query §3] 압축 리프의 키 필터가 함수 열 뒤 열을 공통 접두(펜스) 키에서 읽는다** (.51, 4e389935d, 2026-11-04):
  - `eval_key_filter ()` 는 읽을 키를 속성 순번 j 로 고르고(`(j < prefix_size) ? prefix_midxkey : midxkey`), 원소 위치는 함수 열을 건너뛴 `j + 1` 로 고른다(query_evaluator.c:3550-3551). 함수 열 뒤 열에서 `j + 1 == prefix_size` 면 공통 접두 밖 원소를 prefix 키에서 읽는다.
  - 실측: `(a, sqrt(d), c)` 인덱스를 먼저 만들고 3000행을 넣은 표(리프 압축)에서 `a = 1 and mod(c, 300) = 0` 의 커버드 키 필터가 3행이다(정답 10). `c <> 1500` 은 3000(정답 2999), `between`·`in` 은 0행이다.
  - 접두가 짧거나, 접두 안쪽 열이거나, 함수 열 앞 열이거나, 일반 인덱스거나, 벌크 로드(펜스 키 0)면 맞다.
  - release/11.4 에도 같은 식이 있다(query_evaluator.c:2905-2906, 정적).
  - **미수정**(develop). PR#6466 이 midxkey 위치(`midx_pos`)로 고르게 고친다(미머지) — `repro/G3-01`.
- **[src-query §3] MRO 커버드 출력이 함수 열 위치를 -1 로 넘긴다** (.51, 4e389935d, 2026-11-04):
  - `scan_next_index_scan ()` 의 MRO 분기(scan_manager.c:6282, `multi_range_opt.use` 일 때만)가 부르는 `scan_dump_key_into_tuple ()` 는 `btree_attrinfo_read_dbvalues ()` 에 `func_index_col_id = -1` 을 넘긴다(scan_manager.c:8864-8865). 함수 열이 다른 키 열 앞에 있으면 그 뒤 열을 함수 결과 칸에서 읽는다.
  - 실측: `(i, j, sqrt(d), k)` 에 `where i in (1, 2) … order by j limit 5` 가 `(covers) (multi_range_opt)` 로 가면, k 가 DOUBLE 일 때 k 자리에 sqrt(d) 값이 나온다(조용한 오답). k 가 INT 면 debug abort 다(`qdata_check_output_column`, query_opfunc.c:529).
  - 비 MRO 커버드 경로(`btree_read_curr_key_values`)는 `filter->func_idx_col_id` 를 넘겨 맞다. 함수 열이 맨 뒤면 -1 이어도 맞다.
  - release/11.4 도 같은 `-1` 이다(scan_manager.c:7788-7789, 정적).
  - **미수정**(develop). PR#6466 `d7ce3af72` 가 `iscan_id->indx_cov.func_index_col_id`(develop 에도 있는 필드, 커버링이면 함수 열 위치)를 넘겨 고친다(미머지, 11-05 재실행 정답) — `repro/MRO-c`.
- **[src-parser §3] MRO + WHERE 에만 있는 함수식 + 비커버링이면 XASL 생성이 assert 한다** (.51, 4e389935d, 2026-11-04):
  - `pt_ordbynum_to_key_limit_multiple_ranges ()`(xasl_generation.c:29248)의 `assert (0)`(29318)에서 debug 가 플랜 출력 전에 abort 한다.
  - 실측: `(i, j, sqrt(d), k)` 에 `select j, k from t where i in (1, 2) and sqrt(d) > 0 using index idx(+) order by j limit 5`. develop 은 힌트가 없어도, PR#6466 `d7ce3af72` 는 `NO_COVERING_IDX` 일 때 abort 한다. release 동작은 보지 않았다.
  - **미수정** — `repro/MRO-c` ④.

## PR#6466 head 의 사실 (미머지 — 머지되면 §2 로, 리뷰 코멘트 9건 대응 중이라 바뀔 수 있다)
- 함수 결과는 예약 attr id `FUNC_INDEX_RESULT_ATTRID`(-2)의 의사 속성(도메인 `fi_domain`)으로 키에서 읽는다. 클라이언트가 투영·키 필터의 함수식을 그 속성으로 라우팅한다(`qo_is_coverage_index`·`pt_collect_func_index_cover`).
- 리스트 파일을 거치는 스캔(해시·머지 조인 입력, 조인 아래 정렬, SORT-LIMIT)은 키에 없는 인자를 커버링하면 XASL 생성 뒤 커버링을 끈다(`pt_uncover_func_index_scans`). 비용은 커버링 기준으로 이미 매겨진 뒤다.
