## 확인한 사실 (develop)
- **[src-optimizer §2] HAVING 에는 집계를 왼쪽에 둔 PT_RANGE 가 생기지 않는다** (.51, ef2c78cda, 2026-11-03): HAVING 도 `qo_rewrite_terms` 를 거치지만(query_rewrite.c:486), 비교·BETWEEN·IN 을 RANGE 로 바꾸는 `qo_convert_to_range` 는 왼쪽이 `pt_is_attr`·함수 인덱스 식(PT_EXPR 플래그, parser_support.c:1586-1599)·instnum 일 때만 바꾼다(query_rewrite_term.c:3765-3770). auto-parameterize 도 같은 조건이다(query_rewrite_auto_parameterize.c:67-75). op 에 PT_RANGE 를 대입하는 곳은 query_rewrite_term.c:2965 하나뿐이다. 집계(PT_FUNCTION)는 왼쪽이 될 수 없어 집계 BETWEEN 은 PT_BETWEEN 으로 남는다.
- **[src-optimizer §2] 파생 테이블 card 의 상한은 LIMIT 뿐** (.51, ef2c78cda, 2026-11-03): 파생 테이블 노드의 card 는 하위 XASL 의 `xasl->cardinality` 이고, `pt_get_query_limit_from_query ()` 로 LIMIT 상한만 건다(query_graph.c:1360-1369 → parser_support.c:10570-10590, `info.query.limit`·`orderby_for` 만 읽음). `GROUP BY … LIMIT n` 은 파서가 HAVING 의 `GROUPBY_NUM () <= n` 으로 바꾸면서 `info.query.limit` 을 남기고 `rewrite_limit` 만 0 으로 한다(type_checking.c:7616-7660). 그래서 그 꼴에는 상한이 걸리고, HAVING 에 직접 쓴 `GROUPBY_NUM ()` 에는 걸리지 않는다.
- **[src-optimizer §3] NDV 를 모르는 DISTINCT 가 GROUP BY 의 추정을 입력 행 수로 되돌린다** (.51, ef2c78cda, 2026-11-03): `qo_estimate_ngroups ()` 의 NDV 미상 경로가 `plan->info->group_rows = expected_nrows` 를 무조건 대입한다(query_planner.c:815). GROUP BY 정렬과 그 위의 DISTINCT 정렬은 같은 info 를 쓰고(`qo_sort_new ()` 의 `plan->info = subplan->info`), select list 에 열이 없으면 DISTINCT 의 `qo_get_group_ndv ()` 가 -1 이다. 실측(SA·level 513): 2,000 그룹(그룹 1~7행)에서 `(select distinct count (*) from t group by g)` 파생 테이블 d = 8,005(입력 행 수), 실제 7. 결과 행은 맞다. **미수정**(develop) — PR#8325 가 '낮출 때만 갱신' 으로 바꾼다(미머지, d = 2,000).
- **[src-optimizer §3] 키 필터 아래 GROUP BY 의 그룹 수 과대** (.51, ef2c78cda, 2026-11-03): `qo_estimate_ndv ()` 가 GROUP BY 열 자체를 거른 질의에서 그룹 수를 크게 과대로 잡는다 — 2,000 값 × 100행 표에 `where g <= 100 group by g` 면 d = 1,987, 실제 100(SA·level 513). **미수정**(develop). 별도 이슈 후보.

## PR#8325 head 의 사실 (미머지 — 머지되면 §2 로)
- HAVING 선택도는 `qo_estimate_ngroups ()` 가 GROUP BY 정렬에서 그룹 수 × `qo_having_selectivity ()`(최소 1)로 곱한다. 못 매기는 집계 술어는 `QO_HAVING_DEFAULT_SELECTIVITY` 0.5.
- 첫 EXECUTE 재계획 표시(`hv_pred_walk ()`)와 바인드 감시(`bind_term_walk ()`)는 `histogram_split_hv_predicate ()`·`histogram_split_hv_range ()` 로만 항을 모은다. `SUM·AVG·MIN·MAX (열) op ?` 는 그 열의 술어로 보고, COUNT (*)·집계 BETWEEN 은 보지 않는다. 감시는 SUM 을 `x op ?` 의 행으로 매긴다(플래너는 `x op ? / 그룹 크기`).
- 서버 모드에서 재계획 여부는 `show trace` 의 `Query Plan:` 출력 유무로 보인다. SA(`csql -S`)에서는 PREPARE 덤프 한 번만 보여 가르지 못했다(원인 미확인).
