## §3 예비 이슈 (src/optimizer)

- **[§3] 같은 질의 안에서 비용 순서가 실제 시간 순서와 역전된다 — 34개 중 어긋남 32 / 일치 0 / 동률 2** (.52, `07480dfd1`, 2026-09-18): 옵티마이저가 고른 플랜(base)과 힌트로 찾은 더 빠른 플랜(best)의 루트 비용·확정 측정 시간을 대조. 예외 없이 "더 싸다고 본 쪽이 더 느리다". 예: `16b` 비용 6,862 ↔ 856,864(125배 비싸다고 본 쪽)가 17.444s ↔ 3.768s 로 4.6배 빠르다. `17a` 4,254 ↔ 209,436 / 7.108s ↔ 1.918s. 어긋난 32개에서 놓친 시간 합계 **86.4s**. 탐색 실패가 아니라 **비용 함수가 틀린 것** — 플래너는 틀린 함수의 최소값을 정확히 찾고 있다. **미수정**.

- **[§3] 비용식의 행수 의존 지수가 실측과 어긋나고, idx-join 과 hash-join 이 반대 방향이다** (.52, `07480dfd1`, 2026-09-18): 술어 없는 FK→PK 전수 조인에 PK 범위만 얹어 행수를 바꿔가며 `cost ~ 행수^a`, `time ~ 행수^b` 를 log-log 회귀(R² 0.95~1.00). `mk⋈keyword`: idx a=0.841 vs b=0.997(Δ−0.16), hash a=0.968 vs b=0.788(Δ+0.18). `mc⋈company_name`: idx a=0.820 vs b=1.137(Δ−0.32), hash a=0.917 vs b=0.774(Δ+0.14). 즉 **행수가 커질수록 idx 는 비용을 덜 매기고 hash 는 더 매겨** 격차가 벌어진다. 상수배 보정으로는 고칠 수 없다. 재현: `~/dev/tests/joinorder/scripts/ak_probe_curve.py`. ⚠ **이 측정은 par4 에서 했다** — hash 의 `b=0.78`(선형보다 느림)이 build 분할상환인지 병렬 기여인지 아직 미분리. 직렬 재측정 예정. **미수정**.

- **[§3] 해시조인 가격이 조인 크기에 따라 부호가 뒤집힌다** (.52, `07480dfd1`, 2026-09-18): 카디널리티 오차를 0 으로 만든 프로브(q-error 1.000~1.001)에서 같은 순서·같은 카디널리티로 방법만 바꿔 비용비와 시간비를 대조. 큰 many-to-one 조인은 해시를 **과대계상**(`mk⋈keyword` 비용비 1.90 ↔ 시간비 0.37 = 5.1배, `mc⋈company` 2.01 ↔ 0.44 = 4.6배, `an⋈name` 7.24 ↔ 1.05 = 6.9배), 작은 조인은 **과소계상**(`mi_idx⋈info_type` 0.37 ↔ 1.50 = 0.25배, `title⋈kind_type` 0.42 ↔ 1.35 = 0.31배). 위 행수 의존 항 결함의 귀결. 재현: `scripts/ak_probe_k.py`. **미수정**.

- **[§3 보강] 기존 항목 "조인 카디널리티 `MAX(1.0)` 바닥" — 여러 조인 술어의 선택도 곱이 바닥에 눌린다** (.52, `07480dfd1`, 2026-09-18): `query_planner.c:8390` 루프는 `sarged_terms` 전체를 돌며 `selectivity *= QO_TERM_SELECTIVITY(term)` 로 **곱한다**(즉 조인 술어를 빠뜨리지는 않는다). 문제는 그 다음 두 바닥 — `selectivity = MAX(1.0/MAX(cardinality,1.0), selectivity)` (:8413), `cardinality = MAX(1.0, cardinality)` (:8422). 술어가 여럿이면 곱이 1e-13 급으로 내려가는데 바닥에 눌려 **곱한 효과가 사라진다**. 기존 §3 의 `MAX(1.0)` 바닥 항목(planner_visit_node :8124/:8134/:8158/:8160)과 같은 뿌리. **미수정**.

- **[§2] 카디널리티 오차와 비용가중치 오차는 서로 다른 질의에서 난다 — 순위상관 ρ = −0.004** (.52, `07480dfd1`, 2026-09-18): JOB 113질의 중 두 값이 다 있는 110개에서 스텝 최대 CARD오차와 스텝 최대 k오차(= `(Δcost/Δtime) × CARD오차` 를 같은 조인방법 중앙값으로 나눈 것)를 log 값 Spearman 으로 대조. **ρ = −0.004**, 각자의 중앙값(CARD ×116 / k ×7.3)으로 가른 사분면도 23/33/32/22 로 독립 기대치 27.5 와 사실상 같다. CARD 최상위 무리(`2b`·`17b`·`17a`·`32b`·`17e`, 전부 ×1,231 — 같은 조인 `mk.keyword_id=k.id` 하나 때문)의 k 는 ×2.3~5.0 이고, k 최상위(`5c` ×964 / `11b` ×634 / `8b` ×140)의 CARD 는 ×56 / ×310 / ×446 이다. ✅ **두 결함은 따로 고쳐야 한다** — 카디널리티 추정을 고쳐도 가중치 오차는 그대로 남고, 그 반대도 같다. 두 축 모두 1위인 질의는 `10c` 하나뿐이다(조인 `chn.id=ci.person_role_id` ÷46,393, k ×8,938 — 위 NULL 상관 항목). 재현: 뷰어 <http://192.168.6.52:8828/> 왼쪽 순위도 3개.

- **[§3] 필터가 조인 키의 NULL 여부와 상관돼 있으면 조인 카디널리티가 4~5자릿수 틀린다 — `10c` ÷46,393** (.52, `07480dfd1`, 2026-09-18): `10c` 의 구동 스캔 `cast_info` + `note like '%(producer)%'` 는 **추정 1,430,440 vs 실제 1,435,439 = ×1.003 으로 거의 정확**하다. 틀리는 건 바로 다음 조인 `chn.id = ci.person_role_id` 로, **추정 693,474 vs 실제 15 (÷46,393)**. 추정 통과율 `693,474/1,430,440 = 0.484798` 은 `cast_info.person_role_id` 의 **테이블 전체 non-NULL 비율** `17,571,519/36,244,344 = 0.484807` 과 소수 넷째 자리까지 같다 — 즉 **옵티마이저는 NULL 비율을 정확히 알고 반영한다**(`term sel = 1.54378e-07 = 0.484807 / ncard(char_name) 3,140,339`). 실패는 **상관**이다: 그 필터를 통과한 1,435,439 행 중 `person_role_id` 가 NULL 이 아닌 건 **15개(0.001%)** 뿐이다(프로듀서는 배역이 없다). 선택도는 필터와 조인 키의 NULL 여부를 **독립으로 곱한다**. 기존 §3 "값↔팬아웃 상관" 과 같은 뿌리이되 축이 다르다 — 이쪽은 **NULL 비율의 조건부 분포**다. 실측: `SELECT COUNT(*) FROM cast_info WHERE note LIKE '%(producer)%'` → 1,435,439, `AND person_role_id IS NOT NULL` → 15, 테이블 전체 36,244,344 중 non-NULL 17,571,519. **미수정**.

- **[§2] NULL 조인 키는 프로브 자체를 건너뛴다 — `readkeys` 를 "아우터 행 수" 로 읽으면 안 된다** (.52, `07480dfd1`, 2026-09-18): 위 항목의 부산물. 이너 스캔의 `readkeys` 는 프로브 횟수인데, **조인 키가 NULL 인 아우터 행은 어차피 매칭이 없으므로 엔진이 프로브를 아예 안 한다**. 그래서 `readkeys` = "조인 키가 NULL 이 아닌 아우터 행 수" 다. `10c` 는 구동 스캔이 1,435,439 행을 냈는데 다음 스캔 `readkeys` 가 **15** 다. ⚠ 기존 §2 항목("`readkeys` 가 직전 스텝 출력 행수와 816/864 일치")은 **NULL 이 없는 조인 키에 한해** 성립한다 — 어긋나는 축이 두 개다: **빈손 프로브**(값이 inner 에 없음, `filteredkeys` 와의 차이)와 **건너뛴 프로브**(아우터 키가 NULL, `readkeys` 자체가 줄어듦). 뒤엣것은 `readkeys` 로는 안 보이고 **아우터 스캔의 실제 행수와 비교해야** 드러난다. ✅

- **[§2] 스텝 CARD오차를 볼 때 구동(맨 앞) 스캔을 빼면 그 오차가 k 로 새어 든다** (.52, `07480dfd1`, 2026-09-18): 스텝오차는 "실제 배율 ÷ 추정 배율" 인데 구동 리프는 앞 스텝이 없어 배율을 못 만든다고 보고 `null` 로 뒀었다. 구동 리프는 **물려받은 오차도 없으므로 배율이 곧 `실제/추정`** 이다. JOB 113질의 중 구동 스캔에서 **×2 이상 틀리는 질의가 16개**, 최대 `9a`·`19a` 의 est 96 → act 6,768 (**×70.5**). ✅ 분해 지표를 만들 때 **첫 스텝을 빼면 그 스텝의 오차가 사라지는 게 아니라 다음 지표로 옮겨간다**.

- **[§2] `readkeys`/`filteredkeys` 는 키필터 통계가 아니라 **프로브 적중** 통계다** (.52, `07480dfd1`, 2026-09-18): `btree.c:28077` 이 키를 읽자마자 `read_keys++` 하고, 범위 밖이면 `end_scan` 이라 `qualified_keys` 에는 안 들어간다(:28099). 실측 — **864 리프 중 816 에서 `readkeys` 가 직전 스텝의 출력 행수와 정확히 일치**(qref 레인). 즉 `readkeys` = **프로브 횟수**(아우터 행 수), `filteredkeys` = **결과를 하나라도 낸 프로브 수**, 차이 = **빈손 프로브**(아우터 값이 inner 에 없음)다. `17b` `ci` 는 키필터가 될 술어가 하나도 없는데 41,840→40,832 차이가 난다(1,008개 영화에 배우 기록 없음). ⚠ **이 차이를 키필터로 읽으면 조인 선택도에서 잘못 나눠 빼게 된다** — 미매칭은 "조인이 안 된다" 는 뜻이라 조인 선택도에 **포함돼야 할** 성분이다. ✅

- **[§2] 조인 스텝의 카디널리티는 네 항의 곱으로 정확히 분해된다 — 848/848 실측 일치** (.52, `07480dfd1`, 2026-09-18): `출력행 = 프로브수(readkeys) × 적중률(filteredkeys/readkeys) × 적중당팬아웃(btree rows/filteredkeys) × 데이터필터통과율(lookup rows/btree rows)`. 848개 리프 전부 오차 1% 이내. ✅ 스텝 오차를 볼 때 **어느 항이 틀렸는지** 이 분해로 가른다.

- **[§2] 프로브 적중률은 인덱스 종류로 갈린다 — PK 룩업은 478/478 이 100%** (.52, `07480dfd1`, 2026-09-18): `pk_*` 룩업 478개 **전부 100%**(참조 무결성이 부모 존재를 보장). FK 인덱스 룩업 373개는 100% 211 / 90%+ 53 / 50~90% 75 / **50% 미만 34**. 최저 `15d` `movie_id_aka_title` **4.1%**(10,679 찾아 439), `16a` `movie_id_movie_companies` 22.6%. "자식→부모" 는 항상 맞고 "부모→자식" 은 데이터 나름이다. ✅

- **[§3 보강] 카디널리티 오차의 주범은 미매칭이 아니라 `ncard × sel` 자체다 — `1/NDV` 균등 가정의 실패** (.52, `07480dfd1`, 2026-09-18): 위 분해로 848 리프를 전수 집계하면 **적중률 중앙값 100%, 적중당 팬아웃 중앙값 1.00** 이다. 오차 상위 리프는 **전부 적중률 100%** 이고 틀린 것은 `ncard × sel` 이다. 예: `12b`·`1b`·`1d` 의 `mi_idx` — est 배율 **12,213** vs 실제 **10**(**÷1,221**). `sel = 8.85e-03 = 1/113`(`info_type` 행수의 역수)에 `ncard(movie_info_idx) = 1,380,035` 를 곱해 12,213 이 나오는데 실제로 그 `info_type` 하나에 달린 행은 10개뿐이다. `5c` `mc` 는 est 44,351 vs 실제 798(÷55.6). **113종 info_type 에 138만 행이 고르게 퍼져 있다는 가정**이 깨진 것으로, 기존 §3 "값↔팬아웃 상관"(eqjoinsel 계열)과 **같은 뿌리**이고 이 수치가 그 항목의 강한 근거다. **미수정(구조적)**.

⚠ **정정 이력** (2026-09-18 같은 날): 처음에 이 차이를 "키필터가 걸러낸 것" 으로 읽고 "옵티마이저가 키필터 감소를 반영 안 한다(173개 리프)" 를 §3 으로 올렸으나 **틀렸다**. `readkeys` 가 프로브 수임을 확인하고 위와 같이 정정했다. 이어서 "미매칭률 미반영이 주범" 이라고 본 것도 전수 집계(적중률 중앙값 100%)에서 **소수 사례**로 판명돼 다시 정정했다. 주범은 `ncard × sel` 이다. 또 같은 날 하네스 지표를 두 번 더 고쳤다(위 §2 두 항목): ① 스텝 CARD오차에서 **구동 스캔을 빼 두었던 것**, ② 구동 스캔의 실제 행수를 **다음 스캔의 `readkeys`** 로 읽던 것 — NULL 키 프로브 건너뛰기 때문에 `10c` 가 "구동 스캔 ÷95,363" 으로 잘못 보였다. 지금은 구동 스캔 ×1.003 / 조인 ÷46,393 으로 **오차가 제자리를 찾았다**.

- **[§3] 옵티마이저가 스스로 고른 해시조인이 손해인 사례가 있다** (.52, `07480dfd1`, 2026-09-18): `5c` 는 4스텝 중 3개를 hash-join 으로 고르는데 전 스텝 `NO_USE_HASH` 로 막으면 3.250s → **0.562s (5.8배)**. 최종 답지는 1개만 해시로 써서 0.227s. `31c` 3.364→2.767(1.2배), `25c` 9.078→7.589(1.2배)도 같은 방향. CBRD-26475 로 해시 게이트가 열린 뒤의 비용모델 미보정으로 보인다. **미수정**.

- **[§3 보강] 조인 선택도 `1/NDV` 의 값↔팬아웃 상관 — 수치 근거** (.52, `07480dfd1`, 2026-09-18): 기존 §3 항목(eqjoinsel 계열)에 붙일 실측. `17a` 의 첫 조인 `mk.keyword_id=k.id` 는 추정 card 34 vs 실제 41,840(**×1,231**). 34 는 `movie_keyword` 의 **키워드당 평균 팬아웃**(4,523,930/134,170 = 33.7)과 같고, 필터가 남긴 `'character-name-in-title'` 은 팬아웃 **상위 3위**(41,840 이상이 3개뿐). 팬아웃 분포는 min 1 / max 72,496. **필터 추정 자체는 정확했다**(card 1 vs 실제 1행) — 오차는 전부 조인 스텝에서 난다. 스텝별로 분해하면 `17a`·`16b` 는 **첫 조인 하나만 ×1230 이고 나머지 스텝은 전부 2배 안쪽**이다(누적으로 보면 6개 조인이 전부 ×1000 처럼 보이지만 물려받은 오차다). **미수정(구조적)**.

## §2 분석 — 위 이슈를 재현·검증하려면 알아야 하는 사실

### src/optimizer

- **[§2] 플래너는 구조적으로 left-deep 전용이다 — 어떤 힌트로도 bushy 를 만들 수 없다** (.52, `07480dfd1`): 조인 탐색의 tail 이 항상 단일 노드다(`query_planner.c:7778` `tail_info = planner->node_info[QO_NODE_IDX (tail_node)]`; head 만 다중 노드 prefix, :7769). 예외는 연결 없는 partition 을 합치는 `qo_cp_new`(:10061)뿐이고 힌트로 제어되지 않는다. ✅ 리뷰 체크포인트: "참조 DB 와 플랜 모양이 다르다"를 비용모델 결함으로 오진하지 말 것 — bushy 는 애초에 생성 불가다.

- **[§2] `ORDERED` 는 FROM 순서 전체 사슬을 강제하고 동시에 탐색을 full DP 로 올린다. `LEADING` 은 올리지 않는다** (.52, `07480dfd1`): `add_hint()` 가 노드 i 에 `OUTER_DEP_SET(i) = OUTER_DEP_SET(i-1) ∪ {i-1}` 을 건다(`query_graph.c:4455-4472`). `join_unit` 은 `num_path_inner || (hint & PT_HINT_ORDERED)` 일 때만 `nodes_cnt` 가 되고 아니면 budget 기반(`query_planner.c:9850-9861`, budget 320000 / `QO_JOIN_UNIT_MAX` 8). 즉 **무힌트는 9테이블 이상에서 greedy 부분탐색**을 탄다 — JOB 113개 중 절반이 그 구간. ✅ 힌트 답지와 무힌트 baseline 의 시간 차에는 "탐색 폭" 성분이 섞일 수 있다.

- **[§2] 조인 방법 힌트는 그 스텝의 inner 노드에서만 읽힌다 — FROM 첫 항목에 건 방법 힌트는 무효다** (.52, `07480dfd1`): `qo_examine_idx_join` :6505/:6509, `qo_examine_nl_join` :6639-6641, `qo_examine_merge_join` :6791-6794, `qo_examine_hash_join` :6955-6971(RIGHT OUTER 일 때만 outer 에서 읽음). `ORDERED` 와 함께 쓰면 **조인 하나하나를 지정**할 수 있다(`조인 k 의 방법 = FROM (k+1)번째 별칭의 힌트`). 실측: JOB 113질의 × 3레인 = 339건이 의도대로 실현됐고, 864개 조인 전부를 해시로 만드는 것도 성립한다(전부 등가조인이라). ✅

- **[§2] 힌트 인자 별칭이 하나라도 안 맞으면 그 질의의 힌트 전체가 경고 없이 삭제된다** (.52, `07480dfd1`): `LEADING`/`USE_NL`/`USE_IDX`/`USE_MERGE` 는 REQUIRE_ALL_MATCH → `name_resolution.c:7893-7952`, 실패 시 `:8007-8010` 에서 `hint = PT_HINT_NONE`. 반면 `USE_HASH`/`NO_USE_HASH`/`INDEX_SS`/`INDEX_LS` 는 DISCARD_NO_MATCH(안 맞는 이름만 버림). ✅ 리뷰 체크포인트: 힌트를 쓴 TC·벤치가 "힌트가 안 먹는다"로 보이면 먼저 **별칭 오타**를 의심한다. 실사례 — `~/dev/tests/joinorder/queries/benchmark/answer/31a_answer.sql` 은 `LEADING(it1, …)` 인데 31a 의 FROM 에 `it1` 이 없어 **답지 전체가 무힌트로 실행되고 있었다**.

- **[§2] 강제 순서로 유효 플랜이 안 나오면 플래너가 힌트를 전부 버리고 무힌트로 재플래닝한다** (.52, `07480dfd1`): `qo_optimize_query` 가 NULL → `xasl_generation.c:18255-18300` 에서 `hint_ignored=true`, `hint=PT_HINT_NONE`. detailed dump 의 `[Warning: HINT ignored]` 로만 드러난다. 원인 대부분은 교차곱 스텝(`query_planner.c:8082-8092` `edge_cnt==0`) 또는 `idx_join_cnt==0` 인 스텝의 `USE_IDX`(:8290-8297, :8343). ✅ 힌트 기반 측정은 **반드시 플랜 덤프로 실효를 검증**해야 한다.

- **[§2] `USING INDEX` 부분 목록은 나열되지 않은 테이블을 자유롭게 놔둔다. 테이블별 `alias.NONE` 이 있다** (.52, `07480dfd1`): `add_using_index` 가 `n == 0 && !is_none` 이면 `QO_NODE_USING_INDEX = NULL` 로 남긴다(`query_graph.c:4712-4717`) → 그 테이블은 인덱스 자유 선택. 테이블별 인덱스 금지는 `identifier DOT NONE`(`csql_grammar.y:14227`, `PT_IDX_HINT_CLASS_NONE`). 스키마에 없는 인덱스 이름은 **경고도 로그도 없이** 그 항목만 삭제된다(`view_transform.c:7705-7728` 의 `er_clearid()` + `pt_reset_error()`, `error_log_warning` 기본 false). ✅ 인덱스를 고정하려면 **전 별칭 명시 + 이름 기계 검증**이 필요하다.

- **[§2] merge join 은 `optimizer_enable_merge_join` 이 PRM_HIDDEN·기본 false 라 `USE_MERGE` 없이는 절대 안 나온다** (.52, `07480dfd1`): `system_parameter.c:3548-3553`, `query_planner.c:6806-6810`(힌트 분기 뒤에 와서 USE_MERGE 가 파라미터를 이긴다). JOB 113질의 무힌트 플랜에 m-join 0건. ✅

- **[§2] 현행 develop 의 JOB 무힌트 조인방법 분포 = idx-join 840 / hash-join 24 / nl-join 0 / m-join 0 (864 조인)** (.52, `07480dfd1`, 2026-09-18): 113질의 `SET OPTIMIZATION LEVEL 514` 전수 덤프. 2026-06 분석의 "864 전부 idx-join, 해시 0"은 **낡았다**(CBRD-26475 게이트 제거 효과). 해시가 선택된 질의 14개: `1c 1d 5c 8c 8d 9c 9d 10c 13a 13d 15d 18c 19d 23a`. ✅

- **[§2] 덤프의 `card` 는 정수로 반올림된다 — 1 근처 스텝에서 오차가 부풀려 보인다** (.52, `07480dfd1`): `16a` 의 `t` 스텝 — 진짜 추정은 `34 × 2,528,312 × 3.955e-07 × 2.703e-02 = 0.919` 인데 덤프는 `card 1`. 술어별 오차의 곱은 ÷7.75 인데 스텝 CARD오차는 ÷8.43 으로 찍힌다(`7.75 × 1/0.919 = 8.43`). ✅ 술어별 오차의 곱과 스텝 오차가 8~9% 어긋나면 이 반올림을 의심한다.

- **[§2] 카디널리티 추정은 조인 방법과 무관하다** (.52, `07480dfd1`, 2026-09-18): `natural`/`nohash`/`allhash` 세 레인의 조인 노드 `card` 열이 완전히 동일(`8c`·`8d`·`13a` 확인; `19c` 만 말단 3개가 1→2, 4→6 미세차). ✅ 그래서 q-error 를 한 레인(전 스텝 NL)에서 재서 모든 레인에 공통으로 쓸 수 있다.

### src/query

- **[§2] `SET OPTIMIZATION LEVEL 514` 는 플랜만 찍고 실행을 건너뛴다** (.52, `07480dfd1`, 2026-09-18): `PLAN_DUMP_ENABLED(level) = level >= 0x100`, `OPT_LEVEL(level) = level & 0xff`(`optimizer.h:82-84`). 실측 — 무힌트 19.7초짜리 `16b` 가 **0.017초·0 row** 로 끝나고 `Query plan:` 블록이 나온다. ✅ 플랜 검증·이웃 열거를 **실행 비용 0** 으로 할 수 있다. 단 `SELECT COUNT(*) FROM t`(무술어)는 아예 플랜을 생성하지 않고 메타데이터로 답한다(0.85ms vs 술어 있으면 110ms) — 항진 술어(`id IS NOT NULL`)도 제거되어 같은 fast path 로 간다.

- **[§2] trace 는 병렬 노드의 실제 수치를 본 줄이 아니라 이어지는 줄에 워커별 범위로 준다** (.52, `07480dfd1`, 2026-09-18): `SCAN (table: dba.keyword), (heap time: 10600, fetch: 0, ioread: 0, readrows: 0, rows: 0)` 다음 줄에 `(parallel workers: 2, heap time: 13..10600, readrows: 61257..72913, rows: 61257..72913, gather: buildvalue)`. 본 줄 카운터가 **0** 이므로 이 줄을 안 읽으면 "실제 0행"이라는 거짓을 쓰게 된다. 워커 2개면 min+max 가 곧 두 워커 값이라 정확하다(61,257+72,913 = 134,170 = `keyword` 전체 행수). ✅

- **[§2] 실현 병렬도가 trace 텍스트에 찍힌다 — 설정값이 아니라 실제로 쓴 스레드 수다** (.52, `07480dfd1`): `query_dump.c:3855` `fprintf(fp, ", parallel workers: %d)\n", xasl_p->executed_parallelism)`, 값의 출처는 `query_hash_join.c:197/:215` 의 `manager.num_parallel_threads`. 조건은 `stats_group.status == HASHJOIN_STATUS_PARALLEL && executed_parallelism > 1`. 병렬 스캔은 `query_dump.c:3737` 의 `dump_stats_text`. ✅ 병렬도는 힌트로 못 박지 못하지만 **관측해서 리비전 간 달라지면 무효 표시**할 수 있다.

- **[§2] 해시조인 플랜의 trace 는 구조가 다르다 — HASHJOIN / BUILD / PROBE / SUBQUERY 노드가 있고 중첩 SELECT 가 나온다** (.52, `07480dfd1`): `BUILD (time, fetch, ioread, rows, method: memory)` 가 **빌드 측 행수와 방법**을 준다. ⚠ 루트 SELECT 는 **첫 번째**다 — 중첩 SUBQUERY 안에도 SELECT 가 있어 마지막을 집으면 서브질의 시간을 전체 시간으로 오인한다(`8c` 가 15,885ms 인데 19ms 로 잘못 읽혔다). ✅

- **[§2] `memoize_memory_limit=0` 이면 MEMOIZE 가 꺼지고, 세션에서 바꿀 수 있다** (.52, `07480dfd1`): `memoize.cpp:1046-1050` `if (storage_size == 0) return NO_ERROR;`. 파라미터 플래그가 `PRM_USER_CHANGE | PRM_FOR_CLIENT | PRM_FOR_SERVER | PRM_FOR_SESSION`(`system_parameter.c:5417-5428`, 기본 2MB). ✅ MEMOIZE 가 켜져 있으면 작은 차원 테이블의 PK 룩업이 히트로 걷혀 스캔의 `rows` 가 조인 출력보다 작게 나온다(`1a`: hit 145 / miss 2) — 스텝별 카디널리티 오차가 `÷18267`, `×31071` 처럼 허위로 튄다. 카디널리티 검증에는 반드시 꺼야 한다.

- **[§2] 인덱스 스캔 리프의 감소는 4단계이고 각 단계가 다른 trace 카운터로 나온다** (.52, `07480dfd1`): ① 키레인지(조인 술어) = `readkeys` ② 키 필터 = `readkeys → filteredkeys` ③ 힙 lookup = `btree rows` ④ 데이터 필터 = `btree rows → lookup rows`. ✅ "필터 선택도가 틀렸다"를 판정할 때 ②와 ④를 합쳐 보면 안 되고, 조인 선택도를 계산할 때는 ②④를 **모두 나눠 빼야** 한다(안 빼면 그 감소가 조인 오차로 잘못 찍힌다 — `16a` `mc` 가 ÷11.72 로 보였지만 빼면 ÷2.65).

- **[§2] 이너 리프의 필터 선택도는 무조건부가 아니다** (.52, `07480dfd1`): left-deep 에서 첫 테이블(구동 리프)만 전수 스캔되고 나머지는 조인 키로 프로브된 행만 읽는다. 따라서 이너 리프의 측정 통과율은 **그 조인 키에 조건부**이고 옵티마이저의 테이블 전체 기준 `sel` 과 같은 것을 재는 게 아니다. `16a` `t`: 추정 2.70e-02 vs 측정 3.49e-03(÷7.75) — 필터가 진짜 선택적인지 조인이 유별난 부분집합을 데려온 것인지 이 값만으로는 못 가른다. ✅

- **[§2] JOB 워크로드는 AK-par4 계약에서 IO bound 가 아니라 CPU·버퍼풀 bound 다** (.52, `07480dfd1`, 2026-09-18): 113질의 중 루트 `ioread > 0` 이 11개, 스캔 노드 977개 중 26개뿐. 스캔 `fetch`(논리 페이지) 총합은 2억 322만. `data_buffer_size=16G` + warmup 1패스면 작업 집합이 버퍼풀에 올라간다. ✅ 비용모델의 IO 항이 사실상 무력한 상태에서 CPU 항만으로 비용이 결정된다 — 위 §3 의 행수 의존 항 결함을 해석할 때 전제.
