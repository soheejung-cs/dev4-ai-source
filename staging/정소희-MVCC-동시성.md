- **[src-transaction §3] FK `ON DELETE CASCADE`·`ON DELETE SET NULL`·`ON UPDATE SET NULL` 은 삭제(갱신)하는 트랜잭션의 스냅샷에 보이는 자식만 처리한다 → 부모 없는 자식 행** (.51, `959314906`, 2026-10-21): `locator_check_primary_key_delete()` (locator_sr.c:4244~) 가 RESTRICT/NO ACTION 은 `btree_find_foreign_key()` 로 최신 상태를 보지만, CASCADE/SET NULL 은 `scan_init_index_scan (…, mvcc_snapshot)` + `btree_range_scan (…, btree_range_scan_select_visible_oids)` 로 자식 OID 를 모은다. A 가 자식 INSERT(미커밋) → B 가 부모 DELETE(대기) → A commit → B 성공, 자식 남음. RC·RR 모두, 파티션 자식도. 재현 `repro/R7*.spec`. **미수정** — CBRD-27464(PR#8026, 2팀)에서 수정 중, `locator_check_primary_key_update` 경로 포함(10-23 확인).
- **[src-storage §2] FK 검사는 부모 행에 S 락을 트랜잭션 끝까지 유지한다** (.51, `33d134239`/`959314906`): `btree_check_foreign_key()` (btree.c:26254) 가 `xbtree_find_unique (…, S_SELECT_WITH_LOCK, …)` 로 부모를 찾고, 바로 아래 `/* TODO: For read committed... Do we need to keep the lock? */`(2019). 부모의 키가 아닌 컬럼 UPDATE 와 자식 INSERT 가 서로 막는다(PG 는 9.3 부터 FOR KEY SHARE). **미수정** — CBRD-27463(PR#8198)에서 부모 행 락 제거 중(CBRD-26664 §1, 10-23 확인).
- **[src-storage §3] SA 기동 중 vacuum 이 삭제 파일 페이지에 붙인 TO_VACUUM 표시가 남아 `installdb` 에서 debug assert** (.51, `959314906`, 2026-10-23): `vacuum_find_dropped_file()` (vacuum.c:6664) 의 `pgbuf_notify_vacuum_follows()` → SA 에선 표시가 안 지워진 채 `installdb` → `xboot_soft_rename` → `logpb_rename_all_volumes_files` → `pgbuf_invalidate_all` → `pgbuf_invalidate_bcb()`(더티만 지움) → `pgbuf_put_bcb_into_invalid_list` assert `(flags & PGBUF_BCB_FLAGS_MASK) == 0`. gdb: flags=0x04080000(TO_VACUUM), ptype=12(PAGE_DROPPED_FILES). DROP 이 있었던 DB 를 정상 종료 후 다시 `installdb` 하면 매번(첫 SA 기동만). **미수정**.
- **[src-transaction §2] 로그 페이지 체크섬은 페이지 전체가 아니라 4KB 블록마다 앞뒤 16바이트 표본의 CRC-32** (`logpb_compute_page_checksum`, log_page_buffer.c:455). 복구 분석은 활성 로그 페이지 체크섬이 안 맞으면 부분 flush 로 보고 첫 NULL 블록 위치를 로그 끝으로 삼는다(log_recovery.c:2782, :2883). 오프라인 검산 `~/dev/tests/mvcc/scripts/logcheck.py`.
- **[src-transaction §2] 데드락 희생자는 lock timeout 이 유한하면 abort 되지 않는다** — `lock_select_deadlock_victim()` 이 timeout 가능한 트랜잭션을 먼저 고르고 `lock_wakeup_deadlock_victim_timeout()` 으로 그 대기만 -966 으로 끝낸다(락 유지, 앞선 쓰기 commit 가능 — Oracle ORA-00060 과 같은 문장 단위). 무한이면 `lock_wakeup_deadlock_victim_aborted()` 로 -72. RR 의 -1158 도 문장만 실패.
- **[src-executables §2] debug 서버의 SIGABRT 핸들러는 붙은 클라이언트(CAS)에 SIGABRT 를 보낸다** (server.c `abort_handler`, `!NDEBUG`) — 장애 주입의 기본 동작 `fault_injection_action_prefer_abort_to_exit=yes` 와 겹치면 CAS 덤프가 `$CUBRID/log/coredump` 에 쌓인다. 주입 테스트는 `no` 로.
- **[src-executables §2] `auto_restart_server` 는 master 가 기동 때 `[common]` 에서만 읽는다** (master.c:1521) — DB 섹션 값은 무시된다. 되살린 서버가 등록 전인데 `cubrid server start` 를 겹쳐 부르면 되살린 서버가 등록되지 못해 -677 이 2분쯤 이어졌다(.51 1회 관찰).
