래치 · 락 · MVCC —
세 층의 동시성이 어떻게 구현돼 있나

DB 서버 안에서는 수십 개 스레드가 같은 데이터를 동시에 만집니다. 그런데 왜 안 깨질까요. CUBRID 는 이 문제를 세 층으로 나눠 풉니다. 이 덱은 각 층이 무엇을 지키고 어디에 구현돼 있는지, 그리고 문장별로 무슨 락을 잡고 무엇을 잡지 않는지를 설명합니다.

03래치 규칙

래치는 데드락을 감지하지 않는다 — 순서 규칙과 300초 타임아웃으로 버틴다

1 · 기다릴지 말지

무조건 vs 조건부

UNCONDITIONAL 은 될 때까지 대기, CONDITIONAL 은 안 되면 즉시 NULL. 단, 트랜잭션이 no-wait 상태면 무조건 요청도 조용히 조건부로 강등된다(:2227).

2 · 순서

같은 파일은 페이지 번호 순

pgbuf_ordered_fix 가 강제한다. 두 스레드가 서로 반대 순서로 잡는 일을 처음부터 막는 것이 회피의 전부다.

3 · 그래도 꼬이면

300초 뒤 한쪽을 죽인다

숨은 파라미터 page_latch_timeout_in_msecs. 디버그 빌드는 그 자리에서 assert — "래치 300초 코어" 는 누가 WRITE 래치를 쥐고 안 놓았나를 찾는 문제다.

신입이 지킬 것: 래치를 쥔 채 락을 기다리거나 다른 페이지를 무조건 fix 하지 않는다.

그래서 조심할 것

활성 트랜잭션과 동시에 돈다

힙·인덱스 코드는 "vacuum 이 지금 이 페이지를 치우고 있을 수 있다"를 전제해야 한다. OLD_PAGE_PREVENT_DEALLOC 같은 보호 장치가 성능이 아니라 정합성 장치인 이유.

MVCC 의 대가는 청소다 — PG 는 힙에 버전을 쌓고 vacuum 하고, CUBRID 는 undo 로그에 두고 vacuum 이 로그를 따라간다.

READ COMMITTED (기본)

문장마다

스냅샷을 문장마다 새로 찍고, S 락은 문장이 끝나면 놓는다. UPDATE 는 최신 커밋 버전을 다시 읽어 갱신한다.

REPEATABLE READ / SERIALIZABLE

트랜잭션에 한 번

스냅샷은 시작 때 한 번, S 락은 끝까지. 스냅샷에 안 보이는 행을 갱신하려 하면 SERIALIZABLE 충돌로 거부한다.

14한 문장의 여정

셋은 한 문장 안에서 동시에 움직인다

SELECT … WHERE id = 7

락 IS · 래치 READ · 스냅샷

클래스 IS 만. B-tree root→leaf READ 래치를 잡고 놓고, 힙 페이지 READ 래치. 행 헤더를 스냅샷과 대조 — 너무 새면 undo 로그의 옛 버전.

UPDATE … WHERE id = 7

락 IX+X · 래치 WRITE · 새 버전

클래스 IX → 행 X (남이 쥐면 대기). 힙 페이지 WRITE 래치 → undo 로그 append → 새 버전 기록 → set_dirty → unfix. 커밋 전엔 남들은 옛 버전을 본다.

INSERT … VALUES (8, …)

락 IX + self-lock · 래치 WRITE

클래스 IX + 내 MVCCID 에 X. bestspace 로 빈 자리(busy 면 건너뜀) → WRITE 래치 → 기록. unique 검사자가 이 행을 보면 내 MVCCID 에 S 를 걸고 기다린다.

경계가 보입니다 — MVCC 는 "읽기가 쓰기를 안 기다리게" 하지만, "두 쓰기가 같은 키를 넣는가"(unique/FK) 는 여전히 락의 일입니다.

17함정 셋전부 실제 사례

신입이 밟는 곳은 정해져 있다 — 층을 섞을 때

① 래치 ↔ 락 혼용

래치 쥔 채 락 대기

래치는 함수 안, 락은 트랜잭션 끝까지. 페이지 래치를 쥔 채 lock_object 대기에 들어가면 래치 데드락(감지 없음) → 300초 코어.

② no-wait 속 무조건 래치

조용히 NULL 이 온다

bestspace 처럼 busy 를 정상으로 다루는 호출자와 disk_reserve_sectors 처럼 assert 하는 호출자가 같은 코드에 섞여 있다(CBRD-27198).

③ MVCCID ≠ tran_index

재사용 여부가 다르다

스냅샷·헤더·self-lock 키는 MVCCID, 락 엔트리·TDES 슬롯은 tran_index. 그리고 vacuum 은 지금도 돈다 — 보호 카운터는 정합성 장치(CBRD-27263).
