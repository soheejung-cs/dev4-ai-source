래치 · 락 · MVCC — 세 층의 동시성이 어떻게 구현돼 있나

신입 엔지니어용. "DB 서버 안에서 수십 개 스레드가 같은 데이터를 동시에 만지는데 왜 안 깨지나"를 세 층으로 나눠 설명하고, 문장별로 무슨 락을 잡고 무엇을 잡지 않는지를 표로 정리한다. 모든 주장에 파일:줄을 붙였다 — 코드로 확인하는 습관이 이 문서의 목표다.

핵심 문장 하나. 래치는 "지금 이 순간 이 페이지를 만지는 스레드"를, 락은 "이 트랜잭션이 끝날 때까지 이 데이터의 소유권"을, MVCC 는 "각 트랜잭션이 어떤 버전을 보느냐"를 결정한다. 셋은 서로 대체가 안 된다.

1. 래치 페이지 버퍼가 준다

디스크 페이지는 그냥 못 읽는다. 반드시 페이지 버퍼(pgbuf)를 통해 메모리로 올려서 본다. 진입점이 pgbuf_fix(), 반납이 pgbuf_unfix()다. 래치 없는 fix 는 없다.

pgptr = pgbuf_fix (thread_p, &vpid, OLD_PAGE, PGBUF_LATCH_READ, PGBUF_UNCONDITIONAL_LATCH);
   ... 페이지를 읽거나 고친다 (고쳤으면 pgbuf_set_dirty) ...
pgbuf_unfix (thread_p, pgptr);
신입이 지킬 규칙. 래치는 잡은 함수가 놓는다. 래치를 쥔 채 락을 기다리거나(lock_object) 다른 페이지를 무조건 fix 하지 않는다 — 데드락 감지가 없어서 300초 뒤 코어로 나타난다.

2. 락 락 매니저가 준다

트랜잭션 수준의 소유권. 구현은 전역 해시맵 하나: 키 = LK_RES_KEY(lock_manager.h:148), 값 = 자원 LK_RES(누가 쥐고, 누가 기다리나) + 트랜잭션별 LK_ENTRY. 해제는 트랜잭션 종료에 한꺼번에(lock_unlock_all) — 그래서 2PL 이다.

2.3 대기와 데드락

  • 못 잡으면 자원의 대기 큐에 선다. lock_timeout 이 지나면 ER_LK_UNILATERAL_ABORT.
  • 데드락은 감지 스레드가 lock_detect_local_deadlock(:544)로 wait-for 그래프에서 사이클을 찾아 한 트랜잭션을 희생시킨다.
  • 격리 수준이 영향을 주는 곳은 S 락을 언제 놓느냐다: READ COMMITTED 는 문장이 끝나면 놓고, REPEATABLE READ / SERIALIZABLE 은 트랜잭션 끝까지 쥔다 (lock_unlock_object :7213-7230). 기본은 READ COMMITTED (dbtran_def.h:53).

5. 한 문장의 여정 — 셋이 한 번에 움직인다

SELECT * FROM t WHERE id = 7

  1. 락 클래스 IS. 행 락 없음.
  2. 래치 B-tree root→leaf READ 래치(잡고 놓고), 힙 페이지 READ 래치.
  3. MVCC 행 헤더 insid/delid 를 내 스냅샷과 대조 → 보이면 반환, 너무 새면 undo 로그의 옛 버전.

UPDATE t SET v = 1 WHERE id = 7

  1. 락 클래스 IX → 행 X. 남이 X 를 쥐면 여기서 대기(데드락이면 감지 스레드가 희생 선택).
  2. 래치 힙 페이지 WRITE 래치 → undo 로그 append(WAL) → 새 버전 기록 → set_dirty → unfix.
  3. MVCC 새 버전 insid=나, 옛 버전은 prev_version_lsa 로. 커밋 전엔 남들은 옛 버전을 본다.

INSERT INTO t VALUES (8, …)

  1. 락 클래스 IX + (행 X 대신) 내 MVCCID 에 X = self-lock.
  2. 래치 bestspace 로 빈 자리 찾기(busy 면 건너뜀) → 힙 페이지 WRITE 래치 → 기록.
  3. MVCC 새 행 insid=나. unique 검사하던 남이 이 행을 보면 내 MVCCID 에 S 를 걸고 기다렸다가 root 부터 다시 검사.

여기서 락과 MVCC 의 경계가 보인다: MVCC 는 "읽기가 쓰기를 안 기다리게" 는 해 주지만, "두 쓰기가 같은 키를 넣는가"(unique/FK) 같은 미래의 충돌은 못 막는다. 그건 여전히 락의 일이고, 그래서 self-lock 이 필요하다.

6. Oracle 은 어떻게 다른가 — "행마다 버전을 안 적는다"

사용자 질문: "Oracle 은 MVCC 를 행마다 적지 않는다던데." 맞다. 아래 표에서 매뉴얼로 확인한 것과 일반 지식(매뉴얼 미확인)을 구분했다. 로컬에 있는 Oracle 매뉴얼은 SQL Reference 10gR1 뿐이라 내부 구조(ITL·undo·SCN)는 Concepts 가이드 확인 전까지 매뉴얼 미확인으로 표기한다.

항목OracleCUBRID차이가 뜻하는 것
버전 메타데이터 위치행 헤더에 트랜잭션 ID 를 직접 적지 않는다. 블록 헤더의 ITL(Interested Transaction List) 슬롯에 그 블록을 만진 트랜잭션(XID·undo 위치·commit SCN)을 두고, 행은 그 슬롯 번호(lock byte)만 가리킨다. (매뉴얼 미확인 — Concepts 가이드 없음)행마다 mvcc_insid/mvcc_delid/prev_version_lsa (mvcc.h:38). 블록 단위 슬롯 없음CUBRID 는 행 하나만 봐도 가시성이 결정되고 vacuum 이 행 단위로 정리한다. Oracle 은 블록 단위 슬롯이라 헤더가 작지만 슬롯이 모자라면(ITL 부족) 대기가 생긴다
옛 버전은 어디에테이블 블록엔 최신만. 옛 이미지는 undo 세그먼트. 읽기는 블록의 SCN 이 질의 SCN 보다 새로우면 블록을 복제해 undo 를 역적용한 consistent read 블록을 만든다. (매뉴얼 미확인)같은 방향 — 힙엔 최신 버전, 옛 버전은 undo 로그에 있고 prev_version_lsa 로 따라간다 (heap_get_visible_version_from_log)둘 다 "제자리 갱신 + undo 에서 재구성" 계열. PG 처럼 힙에 여러 버전을 쌓는 방식이 아니다. CUBRID 의 특이점은 undo 가 WAL(트랜잭션 로그) 안에 있다는 것 — 그래서 로그 append 위치(append_lsa)를 읽기 경로가 본다(CBRD-27400)
시점 좌표SCN (System Change Number) 하나MVCCID (64비트 단조) + 스냅샷(lowest_active / highest_completed / 비트맵)CUBRID 는 "활성 집합" 을 비트맵으로 들고 다녀 "커밋됐나" 를 SCN 비교가 아니라 집합 검사로 푼다
읽기와 락"A query never places a lock on a table. Readers never block writers and writers never block readers." (SQL Reference 10gR1, LOCK TABLE, 18-85 / p.1565)SELECT 는 클래스 IS 만 잡고 행 락 없음 (§4). 읽기가 쓰기를 막지 않는 점은 같다. 단 DDL(SCH_M) 은 SCH_S/IS 와 부딪힌다둘 다 reader/writer 비차단. CUBRID 의 IS 는 "DDL 을 막기 위한" 인텐트지 행 보호가 아니다
DML 의 테이블 락UPDATE/INSERT/DELETE 는 자동으로 ROW EXCLUSIVE(=RX) 테이블 락. 모드는 ROW SHARE / ROW EXCLUSIVE / SHARE / SHARE ROW EXCLUSIVE / EXCLUSIVE, LOCK TABLE … IN … MODE [NOWAIT] 로 수동 지정 가능 (18-87~88 / p.1567-1568)UPDATE/DELETE/INSERT 는 클래스 IX (§4). 수동 테이블 락 문은 없고 lock_timeout·no-wait 는 세션/트랜잭션 속성RX ≈ IX, SHARE ≈ S, EXCLUSIVE ≈ X 로 대응. 이름만 다르고 계층 구조(인텐트 → 행)는 같다
행 락의 실체별도 락 매니저 테이블이 아니라 블록 안의 lock byte + ITL (TX 락은 트랜잭션당 enqueue 하나). 행 락 수에 비례해 커지는 전역 구조가 없다. (매뉴얼 미확인)전역 해시맵의 LK_ENTRY — 행 락 수에 비례. 그래서 INSERT 600만 건이 문제가 됐고 self-lock(§5.1)이 나왔다Oracle 의 "트랜잭션당 TX enqueue 하나 + 행은 슬롯 포인터" 가 CUBRID self-lock 의 발상과 닮았다 — CUBRID 는 INSERT 에만 적용했고 UPDATE/DELETE 는 여전히 행 X
정리(청소)undo 는 undo 세그먼트에서 순환 재사용(retention). 테이블 블록은 delayed block cleanout 으로 커밋 표시가 뒤늦게 반영 (매뉴얼 미확인)vacuum 데몬이 로그를 따라가며 delid 가 오래된 버전을 물리 삭제, 산 행은 ALL_VISIBLE 표시 (vacuum.c)CUBRID 는 청소 주체가 별도 데몬이라 "vacuum 이 지금 이 페이지를 치울 수 있다" 를 힙 코드가 항상 전제해야 한다(§7 ③)

Oracle 인용은 로컬 매뉴얼 dev4-oracle-manual/sql-reference-10gR1 의 쪽 번호. "매뉴얼 미확인" 항목은 Oracle Database Concepts 가이드가 리포에 들어오면 절 번호로 바꿔야 한다.

7. 신입이 밟는 함정 셋 (전부 실제 사례)

① 래치로 락을, 락으로 래치를 대신하려 함

래치는 함수 안에서 끝나야 하고 락은 트랜잭션 끝까지 간다. 페이지 래치를 쥔 채 lock_object 대기에 들어가면 래치 데드락(감지 없음) → 300초 코어. 모듈 노트 src-storage §2 리뷰 체크포인트

② no-wait 트랜잭션 안의 무조건 래치

조용히 조건부가 되어 NULL 이 돌아온다(page_buffer.c:2227). bestspace::L1_fix 처럼 busy 를 정상으로 다루는 호출자와 disk_reserve_sectors 처럼 assert 하는 호출자가 같은 코드에 섞여 있다. CBRD-27198 / PR#7630, imports/vimkim/storage/survey-unconditional-page-latch-assumptions

③ MVCCID 와 tran_index 혼동 · vacuum 동시성

스냅샷·헤더·self-lock 키는 MVCCID(재사용 안 됨), 락 엔트리·TDES 슬롯은 tran_index(재사용됨). 그리고 vacuum 은 활성 트랜잭션과 동시에 도니 OLD_PAGE_PREVENT_DEALLOC 같은 보호가 정합성 장치다 — lock-free fast path 가 그 카운터를 반쪽만 회계하는 결함이 열려 있다. CBRD-27263, src-storage §3

8. 확인 퀴즈 — 읽었으면 바로 맞출 수 있는 것

답은 접혀 있다. 먼저 스스로 답한 뒤 연다. 못 맞추면 해당 절을 다시 읽는다.

Q1. 평범한 SELECT 가 잡는 락과 잡지 않는 락은?

클래스 IS(+컴파일 시 SCH_S)만 잡고, 행 락은 잡지 않는다. 행의 가시성은 스냅샷으로 판정한다. → §4 표 1행, heap_file.c:6437

Q2. unique 검사 중 남의 미커밋 삽입 행을 만난 트랜잭션은 무엇을 키로 어떤 모드의 락을 요청하고, 깨어난 뒤 반드시 무엇을 하는가?

inserter 의 MVCCID 를 키로 S 를 요청해 inserter 가 끝날 때까지 기다리고, 깨어나면 S 를 놓고 인덱스를 root 부터 다시 탐색한다. → §5.1, btree.c:27365-27375

Q3. INSERT 가 새 슬롯 행의 X 락을 생략할 수 있는 이유 — 그 락이 하던 두 역할 중 MVCC 가 이미 대신하던 쪽은?

읽기 격리(남이 미커밋 행을 못 보게 하는 것). 이건 insid 가 스냅샷에 안 보이는 것으로 이미 보장된다. 남은 역할인 unique/FK 직렬화는 self-lock 이 이어받았다. → §5.1

Q4. 래치 데드락은 어떻게 처리되는가?

감지하지 않는다. 같은 파일 안 페이지 번호 순서(pgbuf_ordered_fix)로 회피하고, 그래도 꼬이면 300초 타임아웃(page_latch_timeout_in_msecs)으로 한쪽을 죽인다. 디버그 빌드는 그 자리에서 assert. → §1

Q5. READ COMMITTED 와 REPEATABLE READ 의 차이를 락과 스냅샷 두 축으로 말하면?

스냅샷: RC 는 문장마다, RR 은 트랜잭션에 한 번. S 락: RC 는 문장 끝에 놓고, RR 은 트랜잭션 끝까지 쥔다. → §4.1, lock_manager.c:7213-7230

Q6. Oracle 이 "행마다 버전을 안 적는다" 는 말의 정확한 뜻은? CUBRID 와 같은 점 하나, 다른 점 하나.

Oracle 은 블록 헤더의 ITL 슬롯에 트랜잭션 정보를 두고 행은 슬롯 번호만 가리킨다(매뉴얼 미확인, Concepts 가이드 필요). 같은 점: 옛 버전을 테이블이 아니라 undo 에서 재구성한다. 다른 점: CUBRID 는 행마다 insid/delid 를 적고 별도 vacuum 데몬이 청소한다. → §6
