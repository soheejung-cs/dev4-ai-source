2. 분석 내용 (함수별)

항목은 함수 단위로 기술한다. 새 분석도 함수명을 앞세워 추가할 것.

모듈 일반

  • csql_grammar.y는 최대급 bison 문법 — 수정에 극도 주의, bison 재생성이 느림. 문법 변경 후 y.output으로 shift/reduce 충돌 확인.
  • 클라이언트 측 — THREAD_ENTRY * 없음, 서버 측 API 사용 불가.
  • PT_NODE는 union 기반 연결 리스트(node_type + info union + next) — 잘못된 info 멤버 접근은 미정의 동작.
  • 식별자 비교는 전부 intl_identifier_casecmp()(대소문자 무시, base/intl_support.c).
  • 빌드/검증 관점: csql은 클라이언트 코드를 정적 포함한다(ldd에 libcubridcs 없음) — parser/db_vdb 수정 검증 시 so 교체로는 반영 안 됨, csql 재링크 필요. cub_cas는 동적이지만 RPATH가 빌드트리 _install을 가리킴.
  • 리뷰 체크포인트node_type과 접근하는 info union 멤버가 일치하는가?
  • 리뷰 체크포인트식별자 비교에 strcmp류 대신 intl_identifier_casecmp()를 쓰는가?
  • 리뷰 체크포인트문법 변경 후 shift/reduce 충돌이 늘지 않았는가(y.output)?
  • 리뷰 체크포인트서버 전용 헤더/API 의존이 새로 생기지 않았는가?

parser_alloc / pt_append_string (parse_tree.c)

  • 파서 메모리는 parser_alloc(parser, size) — 파서 파괴 시 일괄 해제, 수동 해제 금지. 문자열 복제는 pt_append_string() 또는 parser_alloc + 복사.
  • 리뷰 체크포인트parser_alloc 메모리를 free하거나, 반대로 malloc 메모리를 파서에 맡기지 않는가?

parser_walk_tree (parse_tree_cl.c)

  • 트리 순회는 수동 재귀가 아니라 항상 parser_walk_tree()(pre/post 콜백).
  • 리뷰 체크포인트트리 순회가 parser_walk_tree()를 쓰는가?

pt_compile (compile.c)

  • 95b79e7ed 기준 본문은 PT_SET_JMP_ENV 가드 안에서 pt_semantic_check()를 호출하는 얇은 래퍼 (next 링크를 떼었다 복원). 이름 해석·뷰 변환은 호출자 경로(db_vdb.c 등)에서 별도 단계로 수행된다.

pt_coerce_expr_arguments — 비교 피연산자의 문자열 타입 (type_checking.c:5390)

  • 타입체커는 col <op> 'lit' 에서 CHAR↔VARCHAR 를 PT_ARE_COMPARABLE_CHAR_TYPE 로 보고 리터럴을 컬럼 타입으로 강제변환하지 않는다 (.50, 6497720ec, type_checking.c:5511, 2026-09-17; develop 2d925cb86 같은 줄, 비교 연산자 분기 :5559 "do not cast between numeric types or char types"): 그래서 옵티마이저가 받는 상수 DB_VALUE 의 타입은 리터럴 타입(CHAR)이지 컬럼 타입이 아니다. 호스트변수는 컬럼 타입으로 coerce 된다(6497720ec :9601 — develop pt_eval_expr_type :9571·:9594). 명시 CAST(...) 는 PT_EXPR_INFO_CAST_SHOULD_FOLD 없이는 접히지 않아 qo_classify 가 PC_OTHER → 히스토그램 경로를 안 탄다(1/NDV 폴백). — 정소희(.50) 2026-10-28

pt_check_cast_op — CAST 허용 표 (semantic_check.c:1050)

  • CAST(<date 컬럼> AS INT) 는 실행이 아니라 시맨틱 검사에서 거부된다 (.52, a7a1db84b, 2026-09-16 실측; develop 2d925cb86 정적 재확인 — pt_check_cast_op () 의 DATE → INTEGER·BIGINT·FLOAT·DOUBLE·SMALLINT·MONETARY·NUMERIC … PT_CAST_INVALID(:1159-1178) → MSGCAT_SEMANTIC_CANT_COERCE_TO(:1399)): "Semantic: Cannot coerce [dba.hc].dt to type integer"(-494), prepare 자체가 실패. 런타임 변환 오류를 시험하려면 CAST(<varchar 컬럼> AS INT)(-181)를 쓴다. 1/0 리터럴도 파서가 접으므로 1/? 에 0 바인드. ✅ "실행 시 오류 순서" TC 가 시맨틱 오류로 통과하는 것처럼 보이면 이 함정. — 정소희(.50) 2026-10-28

mq_rewrite_order_dependent_query / pt_has_analytic — 세션 변수 대입의 순서 의존 재작성 (view_transform.c:15579, parser_support.c:3428)

  • ORDER BY + SELECT 목록의 세션 변수 대입은 mq_rewrite_order_dependent_query()(view_transform.c:15579) 가 정렬 파생 테이블 dt_sort 위로 그 항목을 올린다 (.52, 58b49b39f, 2026-10-12; develop 2d925cb86 재확인): mq_translate_select () 가 ORDER BY 가 있을 때 select 목록을 훑어(:6978-7012) 판정 mq_is_order_dependent_node()(:15238)는 PT_DEFINE_VARIABLE, 표시 mq_mark_order_dependent_nodes()(:15310)는 DEFINE/EVALUATE 를 찾고 함수는 arg_list 만 걷는다(분석 함수의 PARTITION/ORDER 키는 안 봄). 대상 항목이 ORDER BY 위치에 직접 있으면 올리지 않는다. e7b1605f5(CBRD-27503) 이후 두 함수는 분석 함수 노드에서 멈추고 순서 독립으로 본다 — 분석 함수는 파생 테이블에 남고, 곁에 있는 대입(sum(i) over () + (@u := i))만 올라간다. — 정소희(.50) 2026-10-28
  • pt_has_analytic() 은 SELECT 에 PT_SELECT_INFO_HAS_ANALYTIC 를 캐시한다 (.52, 58b49b39f, 2026-10-12; develop 2d925cb86 재확인 — parser_support.c:3428): 재작성이 분석 함수를 다른 SELECT 로 옮겨도 원래 SELECT 의 플래그는 남는다 → pt_to_buildlist_proc 가 분석 경로에 들어가 head_list NULL·a_eval_list NULL. e7b1605f5(CBRD-27503 PR#8141) 는 분석 노드를 재작성에서 빼고(위 항목) a_eval_list NULL 을 내부 오류로 막는다(xasl_generation.c:17280) — 플래그 캐시 자체는 그대로다. — 정소희(.50) 2026-10-28

  • host variable 이 섞인 다분기 OR 에서 pt_cnf() 의 공통항 추출이 상수 판과 다르게 동작한다 — 미수정(별건 후보, develop 2d925cb86 재확인 2026-10-28 — 정적: src/parser/cnf.c 는 2026-09-01 이후 변경 없음) (.52, 9ee8bac8b·27171-off 빌드 동일, 2026-09-28): Q19 형태(3분기, brand·quantity 를 ?)에서 (shipmode and shipinstruct and ((br1) or (br2))) or (br3) 로 분기 1·2 만 묶이고 p_partkey = l_partkey 조인 에지가 OR 안에 남는다; 상수 판은 세 분기의 조인 에지·shipmode·shipinstruct 를 모두 빼낸다. 그 결과 qo_extract_or_restrictions() 가 part 전용 conjunct 를 찾지 못해(첫 분기의 conjunct 가 중첩 OR) part 제약이 추출되지 않고 lineitem 제약만 추출된다.
