래치 —
페이지 한 장을 빌리고 돌려주는 규칙

서버 안의 모든 페이지 접근은 pgbuf_fix 로 시작해 pgbuf_unfix 로 끝납니다. 그 사이에 페이지를 지키는 것이 래치입니다. 이 덱은 래치가 무엇을 지키고, 못 받으면 어떻게 기다리고, 언제 조용히 실패하는지를 page_buffer.c 의 실제 코드로 따라갑니다.

02왜 필요한가

페이지는 공유 메모리다 — 두 스레드가 같이 고치면 슬롯 표가 깨진다

래치 없이

스레드 A 가 슬롯 3을 옮기는 도중 B 가 슬롯 4를 넣는다

슬롯 디렉터리의 오프셋과 실제 레코드 위치가 어긋난다. 디스크에 그대로 내려가면 복구도 못 하는 손상이다. 트랜잭션 락은 이걸 못 막는다 — 락은 행의 소유를 가르지, 같은 페이지의 다른 행을 고치는 두 쓰기를 가르지 않는다.

래치로

WRITE 는 혼자, READ 는 여럿

고치려면 WRITE 래치를 받아야 하고, WRITE 를 쥔 동안은 아무도 못 읽는다. 읽기끼리는 같이 든다. 그래서 래치는 짧아야 한다 — 함수 하나 안에서 잡고 놓는다.

래치가 지키는 것은 물리적 일관성입니다. "이 행을 누가 갱신 중인가" 는 락과 MVCC 의 몫이고, 래치는 그걸 모릅니다.

감지 없는 데드락

페이지 래치를 든 채 lock_object 로 들어가면, 그 락을 쥔 트랜잭션이 내 페이지를 기다릴 때 둘 다 300초. 래치는 함수 안에서 끝내고 나서 락을 잡는다.

② 오류 없는 NULL

-2 창에 끼어든 다른 fix

bestspace 가 -2 를 세운 동안 debug 의 페이지 검증이 볼륨 헤더를 fix 하면 강등 → 거부 → 오류 없음 → ASSERT_ERROR_AND_SET 가 죽인다. CBRD-27198 이 볼륨 헤더만 막고(force_latch_wait), PR#8034 가 일반화. 사용자의 lock_timeout=0 도 같은 else 로 떨어진다(:7375, CBRD-27355 미해결).

③ 임시값을 공유 칸에

TDES 에 쓰면 형제가 본다

"잠깐 -1 로 했다 되돌리기" 를 tdes->wait_msecs 에 하면 병렬 워커가 그 사이 그 값을 읽고, 저장/복원이 겹치면 세션에 남는다(CBRD-27183 → 27486). 스레드 값(§09)이 생긴 이유. 아직 TDES 에 남은 자리도 있다 — lock_object_wait_msecs.
