logtb_find_current_wait_msecs / logtb_set_thread_wait_msecs (log_tran_table.c:2657/:2631) — 대기 시간 조회 (CBRD-27486 9699a883c)

  • 락·래치 대기 시간은 "스레드 override 가 있으면 그것, 없으면 tdes->wait_msecs" 다 (.52, PR#8034 head db66b7879 2026-10-01 → 머지 9699a883c 2026-10-06 · develop 2d925cb86 재확인): override 는 THREAD_ENTRY::wait_msecs_override(thread_entry.hpp:266, 기본 LK_WAIT_NOT_OVERRIDDEN)이고 logtb_set_thread_wait_msecs () 가 세우며 이전 값을 돌려줘 복원하게 한다. 락 요청 6경로(lock_manager.c:6340·6499·6721·6861·6955·10302)가 logtb_find_current_wait_msecs () 를 읽고, pgbuf 는 같은 규칙의 inline 사본 pgbuf_find_current_wait_msecs () 를 읽는다(복제·설치 지점 8곳은 src-storage §2 「스레드 스코프 wait override」). TDES 를 바꾸는 xlogtb_reset_wait_msecs () 는 override 가 서 있는 스레드에서 부르면 debug assert 다(log_tran_table.c:2566). — 정소희(.50) 2026-10-28
  • TDES 에 일부러 남긴 자리 — 다른 트랜잭션·교착 탐지기·lockdb 가 봐야 하는 값 (.52, 2026-10-01 · develop 2d925cb86 재확인): 문장 LOCK_TIMEOUT 힌트 (query_executor.c:16955~17094·17840), 온라인 인덱스의 최종 락 승격(xbtree_load_online_index, btree_load.c:7576), compactdb(lock_object_wait_msecs lock_manager.c:6795 — 호출 compactdb_sr.c:566·627, locator_sr.c:11986), lockdb(xlock_dump :9029), composite lock 의 대기 시간 스냅샷(lock_initialize_composite_lock :9132 — 수명이 마무리까지 가서 트랜잭션 값을 쓴다, 머지 커밋 메시지). override 는 워커에 물려지지 않는다(src-thread §2). lock_object_wait_msecs 의 인자가 override 창 안에서 가려지는 잠재 구멍은 §3. — 정소희(.50) 2026-10-28

lock_select_deadlock_victim / lock_detect_local_deadlock (lock_manager.c:5086/:8221) — 교착 희생자

  • 데드락 희생자는 lock timeout 이 유한하면 abort 되지 않는다 — 그 대기만 −966 으로 끝난다 (.51, 959314906, 2026-10-21~23 · develop 2d925cb86 재확인): lock_select_deadlock_victim 은 timeout 가능한 트랜잭션을 먼저 고르고(:5357 "Prefer a transaction with a closer timeout", 같으면 더 젊은 쪽), lock_detect_local_deadlock 이 can_timeout 이면 lock_wakeup_deadlock_victim_timeout ()(:2558, LOCK_RESUMED_DEADLOCK_TIMEOUT → ER_LK_OBJECT_DL_TIMEOUT_SIMPLE_MSG −966)로 그 대기만 끝낸다(:8524-8533) — 락은 유지되고 앞선 쓰기는 커밋할 수 있다(문장 단위 실패). 무한(−1)이면 lock_wakeup_deadlock_victim_aborted ()(:2614 → ER_LK_UNILATERALLY_ABORTED −72, 트랜잭션 abort). RR 의 −1158(ER_MVCC_SERIALIZABLE_CONFLICT)도 문장만 실패한다. — 정소희(.50) 2026-10-28
    • 리뷰 체크포인트동시성 재현의 기대값을 "데드락이면 롤백된다" 로 쓰지 않는다 — lock_timeout 이 유한하면 희생자 트랜잭션은 살아 있고 이후 문장이 커밋될 수 있다.
  • 교착 탐지기는 TDES 만 본다 — override 로 대기 중인 요청의 실제 대기 시간은 보지 않는다 (.52, 2026-10-01 · develop 2d925cb86 재확인): 희생자 선정의 can_timeout 은 LK_CAN_TIMEOUT (logtb_find_wait_msecs (t))(:5249·5325). override 는 페이지 fix 를 감쌀 뿐이라 이것으로 충분하다 — 예외인 log_rollback 의 override 는 두 호출자(log_sysop_abort log_manager.c:4143→4147, log_abort_local :5360→5371)가 먼저 tdes->state = TRAN_UNACTIVE_ABORTED 로 만든 뒤에 서고, 탐지기는 비활성 트랜잭션을 희생자로 고르지 않는다(logtb_is_active (…) == false 를 건너뜀 :5233·5309). 원 메모가 든 세 번째 자리 :8634 는 #if 0 /* NOT_USED */ 안의 lk_global_deadlock_detection 이다. — 정소희(.50) 2026-10-28

lock_set_error_for_timeout / lock_describe_resource (lock_manager.c:2130/:2037) — 락 타임아웃 메시지의 자원 표기

  • 타임아웃 메시지의 자원 문구는 "자원 종류마다 msgcat 문구 하나 + case 하나" 이고, 클래스 이름을 못 구하면 OID 문구로 떨어진다 (.51, PR#7900 a910e8e6e 리뷰 2026-09-17 · develop 2d925cb86 재확인): lock_set_error_for_timeout(:2130) → lock_describe_resource(:2037). heap_get_class_name 이 실패하면 er_clear () 후 MSGCAT_LK_RES_DESC_OBJECT(v|p|slot)로 떨어지고 타임아웃 에러는 정상 설정된다. LOCK_RESOURCE_TRANSACTION 은 inserter MVCCID 를 그대로 찍는다(CBRD-27155 64f02ef62). 함수 머리 주석이 확장 규약을 적는다 — 새 자원 종류는 msgcat 문구 + case 하나, 종류별 타임아웃 에러 코드는 만들지 않는다(ER_IS_LOCK_TIMEOUT_ERROR· LA_RETRY_ON_ERROR·qexec_execute_selupd_list 전부에 넣어야 하고 하나라도 빠지면 동작이 조용히 바뀐다). LK_UNCOND_LOCK 의 대기 시간은 위 「대기 시간 조회」 규칙. — 정소희(.50) 2026-10-28

lock_dump_resource (lock_manager.c:5612) — lockdb 에 보이는 self-lock 대기

  • 미커밋 유니크 키 대기는 lockdb 에 Transaction self-lock (inserter MVCCID = N) 자원 + 대기자 Blocked_mode = S_LOCK 으로 보인다 (.50, 2026-09-18 동적 · develop 2d925cb86 재확인): lock_dump_resource 의 LOCK_RESOURCE_TRANSACTION case(:5748-5750)가 그 줄을 찍고, 대기자는 btree_wait_for_inserter_end (btree.c:27215)의 S 요청이다. 행 X 대기만 찾으면(Blocked_mode = X_LOCK grep) 유니크 삽입 경쟁(예: 첫 통계 수집 경쟁)의 대기를 놓친다 — TC 의 대기 검출을 그렇게 짰다가 오판했다. — 정소희(.50) 2026-10-28

mvcc_satisfies_committed (mvcc.c:639) — 스냅샷 없는 "마지막 커밋 버전"

  • mvcc_satisfies_committed 는 자기 트랜잭션의 미커밋 삽입을 보여 주고, 자기 미커밋 삭제는 숨긴다 (.50, bc988f0ab 코드 확인 2026-09-17 · develop 2d925cb86 재확인): 첫 분기가 !MVCC_IS_REC_INSERTED_BY_ME (…) && MVCC_IS_REC_INSERTER_ACTIVE (…) 일 때만 TOO_NEW 이므로(:643-648) 내가 넣은 미커밋 행은 "committed (or own) insert" 로 SNAPSHOT_SATISFIED(:650-657), 내가 지운 행은 TOO_OLD(:659-662), 남이 지우는 중(미커밋)인 행은 아직 마지막 커밋 버전이라 SATISFIED(:664-668). mvcc_satisfies_dirty 에서 다른 트랜잭션의 미커밋 버전만 뺀 것이고 트랜잭션 스냅샷을 만들지 않는다 — CBRD-27369 0d0809963 이 _db_histogram 의 컴파일 시점 조회에 쓰려고 넣었다. 그래서 committed 무잠금 조회를 존재 확인에 써도 같은 트랜잭션 안의 재호출이 중복 생성을 하지 않는다(오토커밋 OFF 연속 UPDATE STATISTICS). 현재 계약 — 함수 주석이 "새 트랜잭션이 볼 것" 을 원하는 호출자는 자기 dirty 객체를 스스로 빼라고 적는다. — 정소희(.50) 2026-10-28

logpb_compute_page_checksum (log_page_buffer.c:455) / log_recovery_analysis (log_recovery.c:2609) — 로그 페이지 체크섬과 로그 끝
