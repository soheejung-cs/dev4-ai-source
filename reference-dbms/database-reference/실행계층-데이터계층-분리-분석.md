# database-reference 대 CUBRID — 실행 계층 중심 설계 분석서 (2026-09-16)

> 작성: 정소희 (.52) · 원 위치 `claude-workspace/projects/CBRD-27215/` → 2026-09-17 이 리포로 이관(문서지도: 소스·참조 DBMS 분석은 dev4-ai-source). 프로젝트 문맥은 `claude-workspace/projects/CBRD-27215/설계문서-발표.md` D27·D28·NUMERIC 절.

**목적.** 실행기(executor)를 중심으로 두 설계를 축별로 비교해 **우리가 앞선 곳과 뒤처진 곳**을 판정하고,
database-reference가 실물로 갖고 있는 **데이터 계층 분리**(실행 서버 ↔ 스토리지 서버)를 CUBRID에 적용할 때의
경계·단계·비용을 제안한다. 식 컴파일러(`expc`)와 숫자형 비교는 [참조설계-비교-expc.md](expc-식컴파일러-비교.md)에
있으므로 여기서는 요약만 하고 링크한다.

**전제와 한계.**
- database-reference는 **헤더가 정본**이다. `include/server/module/executor` 55개(5.2K줄), `module/data` 131개(15.9K줄),
  `module/buffer_cache` 232개(31.7K줄), `module/transaction` 59개(7K줄)가 있고, **실행기 노드의 `.cc`는 없다**
  (`server/dbsvr/module/sql_compiler/` 아래에 `expression/optimizer/parser/hint`만 존재). 따라서 실행기 쪽 판정은
  "선언과 주석에서 읽히는 데이터 모델·경계"에 대한 것이고, 풀/푸시·디스패치·루프 모양은 판정하지 않는다.
- CUBRID 쪽은 `develop`(`a7a1db84b` 이후)과 PR #7658 브랜치(`9a13c297d`)를 읽었다. 인용은 `파일:행`.
  손댄 모듈 `AGENTS.md`(`src/query`, `src/storage`)와 `cubrid-source-notes` `src-query.md`·`src-storage.md` §2를 대조했다.
- 성능 서술은 **구조에서 도출되는 비용 항**(복사 횟수·래치·행당 분기)까지만 쓰고, 수치는 소스 노트에 측정치가
  있는 것만 인용한다. 나머지는 "측정 필요"로 남긴다.
- 문서·소스 어디에도 참조 제품명을 쓰지 않는다 — "database-reference 참고"로만 적는다(사용자 지시 09-16).

## 0. 한 장 요약

| | database-reference | CUBRID |
|---|---|---|
| 계층을 자르는 자리 | **실행기 아래** — dbsvr(파서·옵티마이저·실행기 상부)와 ssvr(스캔·DML 실행 노드 + 데이터·버퍼·트랜잭션)가 **별도 프로세스/노드**. 스캔·필터·DML이 데이터 옆에서 돈다 | **실행기 위** — 클라이언트 라이브러리(파서·옵티마이저·XASL 생성) ↔ `cub_server`(실행기 + 스토리지 한 프로세스). 실행기와 스토리지는 함수 호출 경계 |
| 노드 사이 통화 단위 | **블록**(`Table` = 블록 핸들 리스트, `Splice`로 O(1) 이어붙임). 버퍼 페이지 핸들과 사설 2KB 청크가 같은 인터페이스 | **행**(`VAL_LIST`의 `DB_VALUE[]`) — XASL 블록 안에서는 포인터, 블록 경계마다 **리스트 파일 튜플**로 물질화 |
| 행 표현 | `RowPiece` 6B 헤더 + 2B 오프셋/컬럼, 청크 바이트 위에 그대로. `RowPos{블록,행번호}`가 해시 가능한 행 참조 | 힙 레코드(OR 표현, 가변 테이블) → `DB_VALUE`(peek) → 리스트 튜플(8B 길이 + 값당 8B 헤더) |
| 컬럼 접근 | 소비자별 사용 컬럼 마스크(`PpNodeUseColumnInfo`: `out/where/key/all`), `ColumnBuilder`가 `Value`를 블록 메모리로 **포인팅**, `Skip()` | 술어/나머지 두 묶음(`pred_attrs`/`rest_attrs`), `data_readval(copy=false)`로 **peek** — 컬럼 단위 포인팅은 이미 한다 |
| 스캔의 데이터 접근 | `Scanner` → `MultiBlockReadHandle` prefetch/fetch(헤더의 `kMultiBlockReadCount = 1`) → **CR 블록**(스냅숏 TSN으로 undo를 적용해 만든 일관 사본)을 핀 | `heap_next` → 페이지 fix → **페이지 사본**(`pgbuf_copy_page_for_scan`, 16KB memmove, 래치 없이 읽기, CBRD-27041) 또는 PEEK+LSA 재검사 → 레코드마다 MVCC 헤더로 가시성 판정 |
| 중간 결과의 자리 | 워커 아레나의 사설 청크(4MB−24 리전) → `MemoryTuner` 피드백 → 넘치면 2-pass 임시 공간 | **항상 임시 파일 페이지**(`QMGR_TEMP_FILE.membuf` 메모리 페이지 N장 → 초과분은 임시 볼륨, pgbuf 경유) |
| 식 평가 | 노드별 레지스터 머신 `expc`(플랜 캐시 상주) | `REGU_VARIABLE` 트리 해석 + **PR #7658의 평탄 스텝 프로그램**(리스트별, 실행 간 재사용) |
| 집계 상태 | `ExAggr = uchar_t*` 바이트 덩어리, 오프셋 0 = count, 기저 함수(COUNT/SUM/SQR_SUM/…)로 분해 | `AGGREGATE_TYPE` 연결 리스트 + 27178 `SUM_ACC`, 셀 기준 SUM/AVG 누산기 공유(D25) |
| 병렬 | 플랜 노드로 분산(`DISTRIBUTION_{SINGLE,RANGE,HASH,BROAD,RR}`, `COLLECTOR`, 병렬 DML/인덱스 빌드) + 테이블스페이스별 ssvr로 스캔 분산 | 한 프로세스 안 워커(`query/parallel/px_*`: 힙 스캔·해시 조인·정렬·쿼리 실행) |

**판정 한 줄.** 실행기 *데이터 모델*(블록 단위 통화, 사설 메모리 중간 결과, 행 참조 `RowPos`)은 database-reference가
앞서고, *식·집계 평가 경로*는 PR #7658 이후 우리가 같은 모양이거나 더 단순하다. **데이터 계층 분리는 database-reference가
프로세스 경계까지 실물로 갖고 있고 그 대가(이중 클래스 계층, 프록시 노드, 두 개의 트랜잭션 컨텍스트)도 소스에 그대로
보인다.** CUBRID는 함수 호출 경계인데 그 경계가 새고 있어(스캔 매니저가 pgbuf LSA를 직접 본다) **분리 1단계(계약 정의)는
비용 대비 가장 확실한 이득**이다.

## 1. 계층 구조 — 어디를 자르는가

### 1.1 database-reference

```
client(JDBC/tci) ──▶ dbsvr ────────────────────────────────────▶ ssvr (테이블스페이스별 N개)
                      parser · optimizer · pp(물리 플랜) · expc            executor 노드(SSVR): TSCAN/ISCAN/DML/MERGE/FOR UPDATE
                      executor 노드(DBSVR/ALL): JOIN·GROUPBY·ORDERBY·WINDOW…  data(table/index/lob) · buffer_cache · transaction(undo/BTS)
                      PROXY_SCAN · *_DBSVR DML 노드(= ssvr 서브트리의 스텁)     space · storage recovery
                      tx_context_dbsvr(ssvr id 집합만 보유)                    tx_context_ssvr(실제 슬롯·undo·redo)
                      StorageManager(테이블스페이스→ssvr 라우팅)
dbmaster(tsmap 공유메모리) · redosvr(redo 적용)
```

- 자르는 자리를 **op 목록이 그대로 말해준다** — `executor/op.list` 95개 op의 마지막 인자가 `ALL | DBSVR | SSVR`이다.
  `TSCAN_*`·`ISCAN_*`는 `ALL`이지만 `PROXY_SCAN`은 `DBSVR`, `INSERT_SSVR/DELETE_SSVR/UPDATE_SSVR/MERGE_SSVR/FOR_UPDATE_SSVR`는
  `SSVR`, 짝인 `*_DBSVR`는 `DBSVR`이다(`op.list:236-255`). `IsProxy()`(`op.h:123`)가 "백엔드 pp를 들고 있는 dbsvr 연산"을 가른다.
- 실행 요청은 메시지다: `InnerInterMsgExecutorDbsvrToSsvr`(`frame/msg/inter_msg_gen.h:4243`) → ssvr의 `ExecuteTaskSsvr`
  (`executor/task/execute_task_ssvr.h`)가 `FindCursor → CursorPrepare → CursorBind → AcquireDmlLock → TransactionBegin →
  PrepareExecutorCm → Fetch → ReplyToTargetDbsvr` 순으로 돈다. 즉 **ssvr에도 커서·바인드·플랜 캐시(`PpSearchByStatement`)가 있다**.
- 라우팅은 `StorageManager::SendToTablespace`(`dbsvr/frame/storage_manager/storage_manager.cc:116`) — 테이블스페이스 id →
  `WorkerStorageProxy` 소켓. 맵은 dbmaster가 공유 메모리로 배포한다(`module/storage/tsmap_server.h`, 32768 엔트리 페이지의 다단 배열).
- 결과는 `Table`(청크 리스트)이 곧 결과 집합이고, 원격 청크는 `ChunkHandle(colcnt, blk, size, copy=false)`로 **받은 버퍼를 그대로 감싼다**
  (`chunk_handle.h:34`). 청크 바이트가 곧 와이어 포맷이다.

### 1.2 CUBRID

```
client lib(cubridcs) ──XASL 스트림──▶ cub_server
  parser · optimizer · xasl_to_stream            qmgr(xqmgr_prepare/execute_query) → qexec_execute_mainblock
                                                 scan_manager(heap/index/list/hash) → heap_file · btree → pgbuf → fileio
                                                 list_file(임시 파일 페이지) · external_sort · lock · MVCC(vacuum)
cub_master(접속 중계) · cub_broker(CAS)
```

- 실행기 ↔ 스토리지는 **같은 프로세스의 함수 호출**이고 타입이 그대로 넘나든다: `HEAP_SCAN_ID`가 `HEAP_SCANCACHE`를
  멤버로 품고(`scan_manager.h:111`), 스캔 매니저가 `pgbuf_get_lsa`·`PGBUF_IS_PAGE_CHANGED`로 **페이지 LSA를 직접 비교**해
  PEEK를 COPY로 되돌린다(`scan_manager.c:5973, :5985-5989`). 데이터 계층의 불변식(CBRD-27094의 IS_LOCK↔X_LOCK 배제,
  `src-storage.md` §2 `heap_scancache_start_internal`)이 실행기 쪽 코드의 안전 근거가 되는 구조다.
- 병렬은 프로세스 안 워커다(`query/parallel/px_scan`, `px_hash_join`, `px_sort`, `px_query_execute`).

**판정.** 어디를 자르느냐는 우열이 아니라 **선택**이다. database-reference의 선택은 데이터 옆에서 스캔·필터·DML을 돌려 네트워크에는
청크만 태우겠다는 것이고, 그 대가로 `cursor/task/tx_context/snapshot/adaptor/block_operator/tx_table`이 전부 `*_dbsvr.h`/`*_ssvr.h`
이중 계층이다(`module/transaction/` 목록에 11쌍). CUBRID의 선택은 단순함이고, 그 대가로 경계가 새는 것을 코드 리뷰로 막아야 한다.

## 3. 행 표현과 이동 — 복사는 어디서 몇 번 나는가

이 절이 [expc 비교 §7](expc-식컴파일러-비교.md)의 "복사 세 번" 판정을 **정정**한다. 소스를 따라가면 CUBRID 힙 스캔의 기본은 peek다.

### 3.1 CUBRID 행 경로 (검증 완료)

```
힙 페이지 ──(a)──▶ RECDES ──(b)──▶ DB_VALUE[] (VAL_LIST) ──(c)──▶ 리스트 파일 튜플 ──(d)──▶ 소비자 DB_VALUE
```

| 단계 | 무엇이 일어나나 | 복사? | 근거 |
|---|---|---|---|
| (a) 페이지 → 레코드 | `heap_next(…, is_peeking)`; `is_peeking = scan_id->fixed`(`ACCESS_SPEC.fixed_scan`, `xasl.h:1104`) → 기본 **PEEK**. 술어 평가 뒤 `PGBUF_IS_PAGE_CHANGED`면 COPY로 **재시도** | 없음(PEEK). 단 **`copy_to_local_cache && is_queryscan`이면 페이지 전체를 사설 버퍼로 16KB memmove**(`heap_file.c:6508-6517`, `pgbuf_copy_page_for_scan` `:7694/:8033`) — 래치 없이 읽기 위한 CBRD-27041의 의도적 사본, 프로파일 2.23%(`src-storage.md` §2) | `scan_manager.c:5905-5989` |
| (b) 레코드 → DB_VALUE | `heap_attrinfo_read_dbvalues` → `heap_attrvalue_read`가 고정/가변 위치를 **포인팅**(`heap_attrvalue_point_fixed/variable`) → `pr_type->data_readval(&buf, …, copy=false)` | 스칼라는 값 복사(그게 값이다), 문자열·NUMERIC은 **레코드 안을 가리킴**(`need_clear=false`) | `heap_file.c:10948-10989, :11073` |
| (c) DB_VALUE → 리스트 튜플 | XASL 블록 출력마다 `qexec_generate_tuple_descriptor` → `qfile_generate_tuple_into_list`(`qexec_end_one_iteration` 안). 값당 8B 헤더 + 8B 튜플 길이(`query_list.h:229-236`) | **복사 1회**. 목적지는 `QMGR_TEMP_FILE.membuf` 페이지(`temp_file_memory_size_in_pages`, `query_manager.c:2882`) → 넘치면 임시 볼륨 페이지(pgbuf 경유) | `query_executor.c:1139`, `list_file.c:1852` |
| (d) 리스트 튜플 → 소비자 | `fetch_peek_dbval TYPE_POSITION` → `qfile_locate_tuple_value` → `data_readval(copy=false /* Don't copy */)` | 없음(peek) | `fetch.c:4726-4737` |

정리: **행당 강제 복사는 (c) 한 번**이고, 그 외는 페이지 사본(a′, 스캔당 페이지 수 × 16KB)과 정렬(`external_sort`)·그룹(재물질화)에서
난다. 압축 컬럼 해제 버퍼처럼 (b)에서 복사가 남는 자리는 CBRD-27448의 범위다.

### 3.2 database-reference 행 경로 (헤더 기준)

```
버퍼 CR 블록 ──TableBlockHandle(핀)──▶ Table ──ColumnBuilder.Build(Value* 포인팅)──▶ expc 평가
   ──InvalidateRowsByFilter(bool*)/Compact──▶ 살아남은 행 ──TableWriter.WriteValues──▶ ChunkHandle(2KB) ──Splice──▶ 다음 노드
```

| 단계 | 무엇 | 복사? | 근거 |
|---|---|---|---|
| 페이지 → Table | `TableBlockHandle(colcnt, BufferHandle* | MultiBlockReadHandle*, idx)` — 버퍼 블록을 핸들로 감싼다 | 없음(핀) | `table_block_handle.h:33-36` |
| 컬럼 접근 | `ColumnBuilder::Build(Value*)` "column 값을 datatype::Value에 pointing 후 다음 Row" / `Skip()` | 없음 | `column_builder.h:52-64` |

### 3.3 판정 — 같은 곳에서 한 번 복사하지만, **목적지가 다르다**

- 둘 다 "투영 지점에서 1회 패킹"이다. 차이는 **패킹 결과가 어디 사느냐**다. database-reference는 워커 아레나의 사설 2KB 청크
  (`kChunkDefaultSize = 2048`, "frame iovec 완성 될 때까지 임시" 주석 — 원래 64KB 의도)이고 필요할 때만 2-pass 임시 공간으로
  내린다(`space/temp_space/executor_2pass_space_controller.h`). CUBRID는 **처음부터 임시 파일 페이지 형식**이고 membuf N장을 넘으면
  임시 볼륨으로 간다 — 페이지 헤더·pgbuf fix/dirty 비용이 붙는다(`src-query.md` "리스트 파일 I/O가 주요 병목이 될 수 있음").
  **→ 뒤처진 곳.** 다만 큰 결과가 디스크로 안전하게 내려가는 것은 CUBRID의 강점이기도 하다 — 메모리 튜너 없이도 OOM이 없다.
- 행 참조: `RowPos{block, row_no}`가 `std::hash` 특수화까지 갖춰 **조인·그룹이 행을 복사 없이 가리킬 수 있다**(`row_pos.h:88-94`).
  CUBRID는 리스트 파일 안 위치(`QFILE_TUPLE_POSITION`)로 비슷한 일을 하지만 해시 키로 쓰는 설계는 아니다. **→ 뒤처진 곳(소폭).**
- 튜플 헤더: `RowPiece` 6B + 2B/컬럼 vs 리스트 튜플 8B + 8B/값. 값 4개 행이면 14B 대 40B. 넓은 투영에서 페이지 밀도 차이. **→ 뒤처진 곳(소폭).**
- 페이지 사본(a′): database-reference는 스냅숏 TSN에 맞춘 **CR 블록**을 버퍼 계층이 만들어 주므로(`adaptor_dbsvr.h GetCrBuf`,
  `buffer_handle_base.h kRequestCurrentCr/kExactCr`) 스캔은 가시성 판정 없이 블록을 읽는다. CUBRID는 페이지를 복사하되
  **레코드마다** MVCC 헤더로 가시성을 본다(`heap_get_visible_version`, 소스 노트: 같은 슬롯 3~4회 재탐색, spage 계열 7.6%).
  이 차이는 §6에서 다시 본다.
- **우리가 앞선 곳:** (b)의 peek는 CUBRID가 이미 한다. §7의 "DB_VALUE로 복사" 판정은 틀렸고, 컬럼 포인팅 자체는 동급이다.
  또 (d)의 `TYPE_POSITION` peek와 XASL position 공유·`pr_share_value`(`src-query.md` "구현 불필요 판정 2건")로 중복 평가도 없다.

## 6. 데이터 계층과 실행기의 경계 — 스토리지 접근

### 6.1 database-reference: `data::FrontendAdaptor` / `data::Adaptor`

- **경계가 클래스 하나로 명시**돼 있다. `FrontendAdaptor`(dbsvr, `adaptor_dbsvr.h:26`)는 "다른 모듈에 요청이 필요한 작업"만 모은다:
  `GetLastDbas`(space), `SetMultiBlockReadHandle/RequestPrefetchBlocks/RequestFetchBlocks`(buffer_cache), `GetCurrentSnapshot`(tx),
  `GetCrBuf/ReleaseCrBuf`(CR 블록 핀), `ExamineCrBuf`(콜백형 검사). ssvr의 `Adaptor`(`adaptor_ssvr.h:28`)가 이를 상속해
  `GetBufForModify/FinishModify`, redo/undo 로그 할당, BTS(블록 트랜잭션 슬롯) 할당·cleanout, 재귀 tx를 더한다.
  → **읽기 경로는 dbsvr에서도 가능하고 쓰기 경로는 ssvr에만 있다**는 것이 타입으로 강제된다.
- `data::Scanner`(`scanner.h`)가 풀스캔 컨텍스트다: `Init()`이 space에 파일 목록을 묻고, `PrefetchBlocks/FetchBlocks`가
  `MultiBlockReadHandle`을 채운다. 주석이 절차를 4단계로 문서화. **헤더의 `kMultiBlockReadCount = 1`** — 멀티블록 읽기가
  선언만 있고 1개로 고정돼 있다(`scanner.h:60`). 설계는 있으나 미완.
- 행 저장 형식(`data/table/rowpiece.h`): `|flags|btsidx|colcnt|twobyte_idx| offsets(colcnt+1) | chn_rpid |` — 오프셋이 **1B/2B 혼합**
  (`twobyte_idx` 이전은 1B), NULL/EMPTY/압축(GCOMP·LCOMP)을 오프셋 센티널로 표현, 체인 행(`kFirstRowPiece/kLastRowPiece/kMigrated`).
  블록(`data/table/block.h`)은 `rpdir[]`에 위치를 두고 **삭제된 rp는 rpdir에 btsidx+1을 적어** 표시(`IsDeletedRp: rpdir[rpno] <= btscnt()`).
- 블록 API가 자유 함수로 분리돼 있다(`data/table/block_api.h`: `AddRowPieces/DeleteRowPiece/LockRows/InsertRowPiece/InplaceColsUpdate…`,
  "기존에 전부 Block의 멤버 메소드로 있어서 분리함") — **단위 테스트 대상**(`data/tests/` 580줄 유틸).
- MVCC는 블록 안 **BTS**(`transaction/common.h:200 BlockTxSlot`, 상태 `INVALID/ACTIVE/COMMIT/FLUSHED/CLEANOUTED`)와 **TSN 스냅숏**,
  읽기는 undo를 적용한 **CR 블록**을 버퍼 계층이 만들어 준다(`cr_block_builder.h`, `cr_candidate_checker_*`). 실행기는 가시성을 모른다.

### 6.2 CUBRID: `scan_manager.c` ↔ `heap_file.c`/`btree.c`/`page_buffer.c`

- 경계는 **함수 집합**이다: `heap_scancache_start`, `heap_next/prev`, `heap_get_visible_version`, `heap_attrinfo_start/read_dbvalues`,
  `btree_range_scan`. 계약을 적은 헤더는 없고 `storage/docs/heap-record-pages.md`가 진입점을 나열한다.
- 새는 곳(경계 위에서 아래 타입을 만지는 자리):
  1. `HEAP_SCAN_ID.scan_cache`(`HEAP_SCANCACHE`)를 스캔 매니저가 소유하고 `page_watcher.pgptr`·`pgbuf_get_lsa`를 직접 읽는다
     (`scan_manager.c:5973-5989`). 가시성·재시도 규칙이 실행기 코드에 있다.
  2. `heap_attrinfo_read_dbvalues`가 **OR 표현 디코드(스토리지 지식)와 DB_VALUE 생산(실행기 요구)**을 한 함수에서 한다 —
     `heap_attrvalue_point_fixed/variable` + `data_readval`. 어느 쪽 모듈의 책임인지 모호하다.
  3. `pgbuf_copy_page_for_scan`(래치 없는 스캔 사본)은 데이터 계층 안이지만, 그 사본 위 포인터의 수명은 실행기가 관리한다
     (`is_peeking → COPY` 전환 판단이 실행기에 있음).
- 가시성은 **레코드마다** 판정한다: `heap_prepare_get_context → heap_get_mvcc_header → heap_get_record_data_when_all_ready`
  (같은 슬롯 3~4회 재탐색, `src-storage.md` §2). CR 블록형과 비교하면 "블록당 1회 vs 레코드당 1회"의 구조 차이인데,
  vacuum이 오래된 버전을 정리한 뒤에는 대부분 레코드가 가시라서 실측 차이는 측정 필요.
- 압축·체인 행·1B 오프셋 같은 저장 밀도 장치는 없고, 대신 **오버플로 레코드**(`overflow_file.c`)와 가변 테이블(`OR_VARINFO`)이다.

## 9. 데이터 계층 분리 — CUBRID에 적용한다면

### 9.1 무엇을 "분리"라 부르나 — 경계 세 겹

| 겹 | 뜻 | database-reference | CUBRID 지금 |
|---|---|---|---|
| ① 계약 경계(모듈 인터페이스) | 실행기가 스토리지에 요구할 수 있는 연산과 **반환 객체의 수명**을 타입으로 고정 | `FrontendAdaptor`/`Adaptor`, `Scanner`, `BlockHandleCommon` | 없음 — 함수 집합 + 공유 구조체 |
| ② 실행 단위 경계(워커) | 스캔·필터를 데이터 옆 워커가 돌리고 실행기는 블록만 받음 | ssvr 워커(`ExecuteTaskSsvr`) | `px_scan`이 부분적으로(결과는 행 슬롯) |
| ③ 프로세스/노드 경계 | 스토리지 서버 분리, 네트워크 위 청크 | dbsvr ↔ ssvr | 없음 |

**제안: ①을 먼저, ②를 ①의 계약 위에서, ③은 하지 않거나 마지막에.** ③의 비용(§7)은 크고, 우리 워크로드(단일 노드)에서 얻는 것은 확인되지 않았다.

### 9.2 ① 계약 경계 — 구체안

**`ROW_SOURCE`(가칭) 계약.** 스캔 매니저가 힙/인덱스에 요구하는 것을 다섯 연산으로 고정한다.

```
open(class, snapshot, column_mask[consumer], filter_prog)  → handle
next_block(handle)                                          → BLOCK_HANDLE | END     /* 페이지 사본 또는 핀 */
bind_columns(block, row_no, mask, DB_VALUE out[])           /* peek, 수명 = block */
release_block(block)
close(handle)
```

- **반환 객체의 수명이 계약이다**: `bind_columns`가 채운 `DB_VALUE`는 `release_block`까지만 유효. 지금 `is_peeking → COPY` 전환 로직
  (`scan_manager.c:5985`)은 계약 뒤로 들어가 실행기에서 사라진다. LSA 재검사·페이지 사본·CR 여부는 **데이터 계층의 구현 선택**이 된다.
- `column_mask[consumer]`: 지금의 `pred_attrs/rest_attrs` 두 묶음을 소비자별 마스크로 일반화(database-reference `PpNodeUseColumnInfo`
  `out/where/key/all`). CBRD-27448의 "소비자별 사용 컬럼 마스크" 항목이 이것이다.
- `filter_prog`: **PR #7658의 스캔 필터 프로그램이 이미 자기완결적 직렬 구조**(스텝 배열 + 셀 + 리터럴 슬롯, 호스트 변수는 E 프롤로그로 분리)라
  계약 아래로 내려 보내기에 맞다. 데이터 계층이 필터를 돌리면 걸러진 행은 `DB_VALUE`를 만들지도 않는다 — database-reference의
  `InvalidateRowsByFilter` 자리에 해당.
- 경계 위에서 금지되는 것: `PAGE_PTR`, `LOG_LSA`, `RECDES`, `HEAP_SCANCACHE`, `OR_*`. 지금 `HEAP_SCAN_ID`의 `scan_cache` 멤버가 첫 제거 대상.

**적용 순서(각각 독립 PR 규모).**
1. `HEAP_SCAN_ID`에서 `HEAP_SCANCACHE`를 감추고 LSA 재검사를 `heap_next` 계열 안으로 옮긴다(동작 동일, 경계 정리만).
2. `heap_attrinfo_read_dbvalues`를 "OR 디코드(스토리지)"와 "마스크에 따른 DB_VALUE 바인딩(계약)"으로 나눈다.
3. 스캔 필터 프로그램 호출 지점을 `eval_data_filter`(`scan_manager.c:5979`)에서 계약 아래로 내린다.
4. 소비자별 마스크(CBRD-27448 ③).

### 9.3 ② 실행 단위 경계 — 블록 단위 통화

- 계약이 서면 `next_block`이 돌려주는 것을 **행 슬롯 대신 블록**으로 바꿀 수 있다. 지금 `px_scan`은 워커가 행을 슬롯에 넣고 소비자가
  하나씩 꺼내는데(`px_scan_slot_iterator`), database-reference처럼 "필터 통과 행의 (블록, 행번호) 목록 + 핀된 블록"을 넘기면
  슬롯당 복사가 없다. 이것이 §3.3에서 뒤처진 "노드 사이 통화 단위"를 좁히는 길이다.
- 중간 결과를 임시 파일 페이지가 아닌 **사설 청크에 먼저** 두는 것(§3.3 첫 항목)은 리스트 파일과 별개의 컨테이너를 요구한다 —
  `QFILE_LIST_ID`의 membuf를 확장하는 방식이 하위 호환에 유리하다(포맷은 그대로, 스필 시점만 늦춘다). 메모리 튜너 없이는
  스필 결정을 못 하므로 **워커별 예산**(간단한 상한)부터.

### 9.4 ③ 프로세스 경계 — 하지 않을 이유를 적어 둔다

- 필요한 것: 와이어 포맷(=청크), 두 트랜잭션 컨텍스트, 스토리지 쪽 플랜 캐시·커서·바인드, 라우팅 맵, 장애 시 `downed_instance_ids_`류 처리.
  database-reference는 이 전부를 이중 클래스 계층으로 지불했다(`*_dbsvr.h`/`*_ssvr.h`, `IsProxy`, `ex_cm_id` 교차 조회).
- 우리 목표(단일 노드 OLAP 질의 시간)에 대해 ③이 주는 것은 "스토리지 노드 추가로 스캔 대역폭 확장"인데, 이는 요구사항이 아니다.
- 결론: **③은 요구가 생길 때. ①·②를 하면 ③의 절반(계약·블록 형식)은 이미 준비된다.**

## 10. PR #7658과의 접점

- 컴파일된 프로그램은 **자기완결적**이라 ①의 `filter_prog`로 바로 쓸 수 있다. 단 프로그램 셀이 `DB_VALUE`를 peek로 품는 지금 구조는
  "셀 수명 ⊂ 블록 수명"을 계약이 보장해야 한다 — 지금은 스캔 매니저가 암묵적으로 보장(같은 행 안에서만 참조).
- D26(도메인 미루기)·D27(호이스팅)은 경계와 무관하게 유지된다. D28 체인은 필터 푸시다운 시 데이터 계층 워커가 그대로 돌릴 수 있다.
- CBRD-27448(가변 길이 값 복사 축소)은 §9.2의 2·4단계와 같은 자리다 — 발번된 이슈에 이 문서를 링크한다.

## 11. 결론 — 우월한 부분과 뒤처진 부분

**database-reference가 앞선 곳**
1. 노드 사이 통화가 **블록 하나**로 통일(버퍼 페이지 핸들 = 사설 청크 = 와이어 포맷)되어 복사 지점이 투영 1회로 고정되고 노드 간 이동은 포인터.
2. 실행기 ↔ 데이터 계층 경계가 **클래스로 명시**(`Adaptor`), 읽기/쓰기 권한이 타입으로 분리, 데이터 계층 단위 테스트 존재.
3. 중간 결과가 **사설 메모리 우선**이고 메모리 튜너 피드백으로 스필 — 우리는 처음부터 임시 파일 페이지.
4. 집계를 **기저 함수 조합**으로 일반화(AVG=SUM/COUNT뿐 아니라 VAR/STDDEV/…); 해시 GROUP BY 상태를 키 옆에.
5. 스캔 가시성은 CR 블록 1회(레코드당 판정 없음) — 구조상 유리, 실측은 미확인.
6. 저장 밀도(1B/2B 오프셋·오프셋 센티널 NULL·압축 심볼·체인 행).
7. 분산이 플랜의 1급 시민이고 스토리지 노드 분리가 실물로 존재.

**CUBRID가 앞선 곳**
1. **힙 → DB_VALUE는 이미 peek**(`data_readval(copy=false)`, PEEK 기본 + LSA 재시도) — 컬럼 포인팅은 동급이고, 이 문서로 §7 판정을 정정한다.
2. 식 평가: PR #7658의 리스트별 프로그램·호이스팅·체인·실행 간 재사용은 database-reference의 expc와 같은 수준이며, **오류 순서·값 공유 규칙이
   문서화·검증(A/B byte 동일)돼 있다**. 조인 조건 컴파일만 결손.
3. **단순성**: 한 프로세스·한 트랜잭션 컨텍스트·한 플랜 캐시. database-reference의 이중 계층(`*_dbsvr`/`*_ssvr` 11쌍, 프록시 노드)은 없다.
4. 큰 중간 결과가 디스크로 **항상 안전하게** 내려간다(메모리 튜너 없이도 OOM 없음).
5. 헤더에 선언만 있고 구현이 없는 op가 절반인 참조와 달리, 우리 17개 proc 타입은 전부 살아 있는 코드다.

**같은 수준**
- 행 단위 스칼라 식 평가(둘 다 벡터화 없음), 임시 공간 관리, 래치 없는 스캔 사본, 멀티블록 프리페치(둘 다 미완).

**다음 행동(우선순위)**
1. §9.2 1단계 — `HEAP_SCAN_ID`에서 `HEAP_SCANCACHE`·LSA 재검사를 데이터 계층 안으로(동작 동일, 발번 필요).
2. CBRD-27448을 §9.2 2·4단계로 확장 정의.
3. 집계 기저 함수 분해(VAR/STDDEV까지 누산기 공유) — D25의 일반화, 별도 발번.
4. 측정 먼저: 리스트 파일 페이지 vs 사설 청크의 실제 차이(TPC-H Q1/Q3의 물질화 지점), 레코드당 가시성 판정 비용.
